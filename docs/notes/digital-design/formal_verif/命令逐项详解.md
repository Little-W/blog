# VC Formal 命令逐项详解

本文件汇集了各章节的 200 个命令及其应用用法条目，按用途组织，便于全文检索。语法部分保留原命令和参数名称，中文解释说明其作用、选项、执行条件和结果；完整的工程源码保留在应用教程正文中。这里的用法不是经过授权工具实际执行的结果。

## 1. 启动、编译与环境

### 1.1 `vcf`：启动外壳、批处理和图形会话

```text
vcf [-batch] [-out_dir <dir_name>]
    [-cmd_log_file <log_name>] [-f <file_name>]
    [-fmode <FPV|COV|SEQ|CC|AEP|FRV|FXP|FSV|FUSA|DPV>]
    [-gui] [-verdi] [-verdi_base] [-verdi_apex]
    [-help] [-id] [-lic_wait <minutes>] [-no_init]
    [-no_restore] [-no_ui] [-output_log_file <log_name>]
    [-read_only] [-reset] [-restore] [-session <session_name>]
    [-use_ipv4] [-use_ipv6] [-x <config_tcl_cmd>]
    [-y <post_config_tcl_cmd>] [-doc]
    [-fml_base] [-fml_ultra] [-fml_elite] [-fml_token]
    [-fml_legacy] [-fml_no_legacy] [-fml_zoix] [-fml_z01x]
    [-fml_auto_restore_level <none|job|engine|host|all>]
    [-scl_span] [-rma_off] [-container] [-noecho]
    [-fml_nxg <0|1|2>] [-echo]
```

**参数解释。** `-f` 指定启动后执行的 Tcl 脚本，完整写法为 `-file`；`-batch` 进入非交互批处理，`-out_dir` 指定输出目录，`-session` 指定运行数据库目录。`-cmd_log_file` 保存命令记录，`-output_log_file` 保存控制台输出，两者用途不同。`-fmode` 选择启动应用，省略时为 FPV，启动列表不含 FTA。

`-gui` 和 `-verdi` 打开图形环境；`-verdi_base`、`-verdi_apex` 选择相应的 Verdi 授权。`-fml_base`、`-fml_ultra`、`-fml_elite`、`-fml_token` 选择形式工具授权方式；`-fml_legacy` 使用旧授权查找，`-fml_no_legacy` 不回退到旧方式，两个 FuSa 选项选择分级 FuSa 授权。`-lic_wait` 的单位为分钟，`-scl_span` 允许跨多个服务器获取授权。

`-restore` 恢复会话，`-read_only` 只读恢复；`-no_restore` 删除以前会话并重新开始，`-reset` 清理旧工作会话，使用前应保留需要的数据库。`-no_init` 不读初始化设置文件，`-no_ui` 不启动界面进程。`-x`、`-y` 分别在配置阶段及配置后执行 Tcl 命令。`-fml_auto_restore_level` 控制自动保存会话的恢复层级。`-rma_off` 关闭相应授权模式下自动启用的回归加速，`-container` 用于容器环境；`-use_ipv4`、`-use_ipv6` 选择进程通信协议；`-fml_nxg` 选择命令一致性模式。`-noecho` 不在输出与会话日志中回显命令；`-echo` 只回显环境而不调用可执行程序。`-help` 显示帮助，`-id` 显示构建和环境信息，`-doc` 打开文档。

**用法与结果。** 这是操作系统命令，不是在 `vcf>` 提示符内执行的 Tcl 命令。批处理脚本必须等待需要的证明完成，再导出报告和退出；只加 `-batch` 并不会替脚本中的所有异步命令建立依赖。每个回归任务使用独立会话目录，避免多个进程同时写入同一个数据库。

```tcl
vcf -f scripts/fpv_counter.tcl -batch \
    -session counter_run -output_log_file counter.log
vcf -f scripts/fpv_counter.tcl -verdi
vcf -restore -session counter_run -read_only
```

来源：User Guide，X-2025.06-SP1，第 54–62 页。

### 1.2 `help`：按命令名称查询帮助

```text
help [<command-pattern>]
```

**参数解释。** 不指定模式时显示帮助入口；模式可以包含通配符，例如用 `report*` 查找报告类命令。这里的星号用于匹配命令名称，不是筛选设计对象。

**用法与结果。** 先确认命令是否存在，再查看它的参数。未知命令和未知参数是两个不同的问题：前者可能来自应用模式、安装包或命令版本，后者通常需要核对具体的调用形式。

```tcl
help
help report*
```

来源：User Guide，X-2025.06-SP1，第 46–50；Quick Reference Guide 6 页。

### 1.3 `man`：阅读命令的详细手册页

```text
man <command-name>
```

**参数解释。** 命令名本身不带参数。详细页通常给出用途、语法、参数和示例，适合核对本文调用形式之外的选项。

**用法与结果。** User Guide 对部分平台命令会明确转引 VC Static Platform Reference Guide，因此不能把 User Guide 中的一行示例当成命令所支持的全部参数。

```tcl
man report_fv
man create_clock
```

来源：User Guide，X-2025.06-SP1，第 46–50；Quick Reference Guide 6 页。

### 1.4 `view_help`：打开图形帮助条目

```text
view_help <command-name>
```

**参数解释。** 指定要查看的命令名称。图形帮助依赖可用的文档和界面环境。

**用法与结果。** 它只用于阅读说明，不运行这个命令，也不改变当前验证状态。在批处理环境中应优先保存文本帮助和命令日志。

```tcl
view_help report_fv
```

来源：User Guide，X-2025.06-SP1，第 46–50；Quick Reference Guide 6 页。

### 1.5 `set_fml_appmode`：选择形式应用

```text
set_fml_appmode <FPV|COV|SEQ|CC|AEP|FRV|FXP|FSV|FUSA|DPV|FTA>
```

**参数解释。** 位置参数是应用模式名。FCA 是覆盖分析应用的名称，本文采用该版 User Guide 明确列出的 Tcl 模式 `COV`；FTA 可以通过这个命令切换，但不能用 `vcf -fmode FTA` 启动。

**用法与结果。** 通常应在编译前选定应用。FTA 的例外流程是先在 FPV 中准备并运行属性，再切换到 FTA。切换模式并不意味着已加载的专用配置、故障数据库或证明条件会自动生效。

```tcl
set_fml_appmode FPV
get_fml_appmode
```

来源：User Guide，X-2025.06-SP1，第 64–65 页。

### 1.6 `get_fml_appmode`：查询当前应用模式

```text
get_fml_appmode
```

**参数解释。** 无位置参数，返回当前形式应用名。

**用法与结果。** 在公共脚本入口以及切换到专用应用之后各查询一次，可以及早发现使用了错误的默认模式。不要用 GUI 页签的名称代替对实际 Tcl 模式的检查。

```tcl
set current_app [get_fml_appmode]
puts "Current application: $current_app"
```

来源：User Guide，X-2025.06-SP1，第 65 页。

### 1.7 `set_app_var`：设置平台应用变量

```text
set_app_var <variable-name> <value>
```

**参数解释。** 第一个参数是平台登记的应用变量，第二个参数是符合该变量类型和值域的值。变量是否要在读入设计前生效，应根据变量说明来确定。

**用法与结果。** 这个命令不同于 Tcl 的 `set`：后者可以创建普通的脚本变量，而这个命令针对的是工具已定义的应用变量。编译开关、前端行为和形式求解变量不能混为一类。

```tcl
report_app_var apply_bind_in_all_units -verbose
set_app_var apply_bind_in_all_units false
```

来源：User Guide，X-2025.06-SP1，第 63–64、119 页。

### 1.8 `report_app_var`：查询平台变量的值和说明

```text
report_app_var [<name-pattern>] [-verbose]
```

**参数解释。** 不指定模式时列出平台变量；模式用于限定名称范围，`-verbose` 显示详细说明。输出会区分当前值、类型、默认值和限制。

**用法与结果。** 报告平台变量时，并不会把用户通过 `set` 创建的所有普通变量都列出来。需要审计配置时，应同时保存设置脚本和相关的详细报告，而不是只记录修改后的某一个数值。

```tcl
report_app_var fml_*
report_app_var fml_composite_trace -verbose
```

来源：User Guide，X-2025.06-SP1，第 63–64 页。

### 1.9 `set_fml_var`：设置形式分析变量

```text
set_fml_var <variable-name> <value> [-global]
```

**参数解释。** 变量名决定要控制的对象，例如运行时间、内存、空洞性分析或轨迹生成。`-global` 在文档示例中用于把设置应用到所有任务；并不是每项变量都能在求解过程中即时修改。

**用法与结果。** 变量既可能改变模型，也可能只改变资源。前者需要重新构建并复核结果，后者也要在任务开始前明确设定。不要把缩短时间限制后遗留的未完成目标算作成功。

```tcl
set_fml_var fml_max_time 24H
set_fml_var fml_max_memory 32GB
set_fml_var fml_vacuity_on true
set_fml_var fml_report_profile_data true -global
```

来源：User Guide，X-2025.06-SP1，第 131–132、709–713；Quick Reference Guide 7–8 页。

### 1.10 `report_fml_var`：查询形式变量

```text
report_fml_var [<name-pattern>] [-verbose]
```

**参数解释。** 名称模式支持按前缀查找；`-verbose` 用于查看默认值、当前值和具体说明。

**用法与结果。** 文档基线相同，也可能启用了不同的安装配置。对于影响覆盖生成、初始状态或抽象的变量，应先查看详细说明，再在正式脚本中显式设置需要的值。

```tcl
report_fml_var fml_max_*
report_fml_var fml_vacuity_on -verbose
```

来源：User Guide，X-2025.06-SP1，第 384、1127–1140；Quick Reference Guide 6 页。

### 1.11 `read_file`：一次读入、编译并展开设计

```text
read_file -format <verilog|sverilog|vhdl> -top <top-name>
          [-sva] [-aep <aep-types>] [-cov <coverage-types>]
          -vcs {<compiler-options-and-files>}
```

**参数解释。** `-format` 选择语言，`-top` 指定顶层，`-sva` 启用对源代码属性的处理。`-aep` 和 `-cov` 是相应应用的目标生成选择，不能在任意应用中随意组合。`-vcs` 后的一个 Tcl 参数会传给编译前端，可以包含文件名、文件列表和前端选项。

**用法与结果。** 这是 User Guide 展示的一步流程，并不是平台参考手册中的全部选项。推荐用花括号包住固定的编译参数串，避免 Tcl 提前替换方括号和美元符号；需要变量展开时，则使用经过审查的双引号或 `list` 构造。设计文件、属性文件和绑定文件必须全部被编译。

```tcl
set_fml_appmode FPV
read_file -format sverilog -top counter -sva \
    -vcs {-f filelist_counter.f}
```

来源：User Guide，X-2025.06-SP1，第 118–120、371、394–395 页。

### 1.12 `analyze`：分析源文件并存入设计库

```text
analyze -format <verilog|sverilog|vhdl> [-library <library-name>]
        [-vcs {<compiler-options>}] <source-files>
```

**参数解释。** `-format` 指定前端语言，`-library` 用于区分分析库；源文件既可以直接给出，也可以使用文档中的 `-vcs` 参数串和文件列表形式。

**用法与结果。** 这一步只完成前端分析，并不等于已经建立可证明的顶层设计。混合语言工程可以分别分析 VHDL 和 SystemVerilog，再通过 `elaborate` 统一展开；SEQ 常为参考实现和待比较实现使用不同的库。

```tcl
analyze -format sverilog -vcs {-f filelist_counter.f}
elaborate counter -sva
```

来源：User Guide，X-2025.06-SP1，第 119–120、522–523 页。

### 1.13 `elaborate`：展开顶层并建立验证设计

```text
elaborate <top-name> [-sva] [-aep <aep-types>]
          [-cov <coverage-types>] [-vcs {<compiler-options>}]
```

**参数解释。** 顶层名来自已经分析的设计单元。`-sva` 处理属性，`-aep`、`-cov` 指定相应的自动目标。混合语言绑定有时需要额外的前端选项，User Guide 给出了与绑定相关的 `-lca` 示例。

**用法与结果。** 展开后应检查顶层、实例层级、参数值、黑盒以及属性数量。对于参数化模块，仅仅成功分析文件，并不能保证展开的就是要验证的那个参数配置。

```tcl
analyze -format sverilog -vcs {-f filelist_counter.f}
elaborate counter -sva
report_fv -list
```

来源：User Guide，X-2025.06-SP1，第 119–120、375–376 页。

### 1.14 `set_blackbox`：把选定模块或实例设为黑盒

```text
set_blackbox -designs <module-name-list>
set_blackbox -cells <hierarchical-instance-list>
```

**参数解释。** `-designs` 按设计单元名称选择模块，可能影响它的多个实例；`-cells` 选择具体的层级实例。层级名称应与当前顶层下的展开结果一致。

**用法与结果。** 黑盒会省略内部功能，其输出通常成为模型中的自由输入。这样可以缩小问题规模，也可能产生真实实现中并不存在的行为。对证明通过与失败的解释必须结合抽象方向；安全信息流应用还需要专门的安全黑盒设置，不能直接沿用普通黑盒的推断。

```tcl
set_blackbox -designs {large_memory}
set_blackbox -cells {u_soc.u_analog}
report_blackbox
```

来源：User Guide，X-2025.06-SP1，第 128–131；Quick Reference Guide 7 页。

### 1.15 `report_blackbox`：报告黑盒对象

```text
report_blackbox
```

**参数解释。** 无参数形式会输出当前的黑盒配置及对象。

**用法与结果。** 在运行前应比对预期的黑盒和实际的黑盒。未解析模块、显式黑盒以及工具优化得到的结构，应按来源分别记录；缺少源文件不应被当成合理的抽象。

```tcl
report_blackbox
```

来源：User Guide，X-2025.06-SP1，第 128–131；Quick Reference Guide 7 页。

### 1.16 `get_blackbox`：取得黑盒集合

```text
get_blackbox
```

**参数解释。** 返回当前设计中的黑盒对象，供后续 Tcl 查询使用。

**用法与结果。** 返回值是工具对象集合，而不是普通的文本报告。检查它的大小、名称和层级时应使用集合命令；不要仅根据控制台截断显示的几项，就判断黑盒已经全部列出。

```tcl
set boxes [get_blackbox]
puts [sizeof_collection $boxes]
foreach_in_collection box $boxes {
    puts [get_object_name $box]
}
```

来源：User Guide，X-2025.06-SP1，第 128–131；Quick Reference Guide 19 页。

### 1.17 `create_clock`：定义时钟及参考时钟

```text
create_clock -period <period_value> [-name <clock_name>]
             [-waveform <edge_list>] [-add] [-comment <string>]
             [-refclk] [-initial <0|1>] [source_objects]
```

**参数解释。** `-period` 是时钟周期；`source_objects` 是定义时钟的网络、端口或引脚。`-name` 指定时钟对象名，`-waveform` 给出边沿列表，`-add` 向原时钟补充选项，`-comment` 保存说明。`-refclk` 指定参考时钟；`-initial` 指定时间零时刻的时钟值，本版列出的默认值是 1。

**用法与结果。** 参考时钟用于没有显式时钟的脚本属性、复位仿真以及部分深度报告。单时钟设计会自动使用该时钟，多时钟设计默认选择最快的时钟，也可以显式覆盖。相同的 `-name` 再次用于不同信号会覆盖原时钟，因此不同的真实时钟应使用不同的名称。周期表达的是相对时间关系，不应把数值直接当成芯片在真实电压、温度下的工作频率证明。

```tcl
create_clock clk -name core_clk -period 100 -refclk
create_clock slow_clk -name peripheral_clk -period 200 \
    -waveform {0 100} -initial 0
```

来源：User Guide，X-2025.06-SP1，第 132–138 页。

### 1.18 `create_reset`：定义复位有效值及启动复位

```text
create_reset [-sync] [-async] [-both] [-type <reset|set|both>]
             [-name <reset_name>] [-sense <low|high|any>]
             [-value <low|high>] [-add] [-tdr]
             [-disable_assertions_db] [-untimed] [source_objects]
```

**参数解释。** `source_objects` 是实际的复位信号，不能只写对象名而不给源信号。`-sense low` 表示低有效，`-sense high` 表示高有效；共享平台帮助推荐用 `-value` 代替 `-sense`，但本版形式流程的正文仍用 `-sense` 解释行为。

`-sync`、`-async`、`-both` 描述复位连接的类型，缺省为异步；`-type`、`-name`、`-add` 分别描述类别、命名和选项追加。`-tdr` 标记测试或调试复位，`-disable_assertions_db` 关闭对应的 AssertionDB 生成，`-untimed` 表示不是时序单元的时钟化输出。User Guide 特别指出，VC Formal 的关键行为由复位有效电平决定，不能把共享平台的全部标记都理解为额外形式约束。

**用法与结果。** 低有效复位在初始化仿真时被施加为 0，在后续形式分析中被固定为 1；高有效的情形则相反。因此标准流程验证的是复位之后的工作行为，而不是运行过程中随意的再次复位。要验证动态复位，必须另建允许复位变化的模型和相应属性。`create_reset -name rst` 不等价于 `create_reset rst`，工具不支持用这种写法创建虚拟复位。

```tcl
create_reset rst_n -sense low
sim_run -stable
sim_save_reset
```

来源：User Guide，X-2025.06-SP1，第 138–140 页。

### 1.19 `get_resets`：查询复位对象

```text
get_resets [-filter <filterexp>] [-regexp] [-quiet] [-nocase]
           [-exact] [-of_objects <object-list>] [patterns]
```

**参数解释。** `patterns` 匹配复位名称；`-filter` 根据属性筛选，`-regexp` 采用正则表达式，`-exact` 要求精确匹配，`-nocase` 忽略大小写，`-quiet` 抑制提示信息。`-of_objects` 从端口、引脚、网络或复位根对象查询关联的复位。

**用法与结果。** 查询出的对象应与真实的复位域逐项对应。读入设计后如果增加了封装层，路径必须相对新的顶层修正；名称看起来相近，并不保证选中的就是实际复位源。

```tcl
get_resets
get_resets rst*
get_resets -filter {name == rst_n}
```

来源：User Guide，X-2025.06-SP1，第 140 页。

### 1.20 `set_constant`：同时约束初始化与正式分析中的常量

```text
set_constant <signal-or-object-list> -value <constant>
```

**参数解释。** 信号对象是要固定的端口或网络，`-value` 给出数值。Verilog 数字可以带位宽，例如 `1'b0`，传入脚本时应保持正确的 Tcl 字面值。

**用法与结果。** 常量传播能简化后续逻辑，但它不是一条属性，不能像 `fvassume` 创建的约束那样转换成断言。与普通假设相比，它还参与复位状态的计算。只能固定当前功能模式下确实恒定的信号；固定模式选择之后，其他模式就不在本次结论的范围之内。

```tcl
set_constant scan_en -value 1'b0
set_constant test_mode -value 1'b0
```

来源：User Guide，X-2025.06-SP1，第 70 页。

### 1.21 `set_change_at`：限制输入允许变化的时钟事件

```text
set_change_at -clock <clock-name> [-posedge] [-negedge] <signals>
set_change_at -clock <clock-name> -default
set_change_at -default -remove
```

**参数解释。** `-clock` 指定控制输入变化时机的时钟，边沿选项进一步指定允许变化的事件；`-default` 设置默认信号规则，`-remove` 移除对应规则。这里展示的是 User Guide 和快速参考中出现的调用形式。

**用法与结果。** 在慢时钟上写一个 assume，只能保证慢时钟采样点上的条件，并不会自动保证两个采样点之间保持稳定。在多时钟验证中，快时钟可能看到中间的变化。这个命令用于表达真实接口的稳定区间，不能把本来异步变化的输入强行同步化来消除失败。

```tcl
set_change_at -clock clk -default
report_change_at
```

### 1.24 `sim_run`：运行初始化仿真

```text

```

**参数解释。** `-stable` 运行到用于初始化的稳定状态；数值形式运行给定的周期数，`-clk` 指定计数所用的时钟。

**用法与结果。** 这个命令服务于形式模型的初始化，并不等于覆盖设计全部工作行为的动态验证。运行后用 `sim_get` 检查关键寄存器，再执行 `sim_save_reset`，把得到的状态交给证明。修改会影响形式设置的条件之后，工具可能重新生成复位状态，需要避免覆盖手工初值。

```tcl

sim_get [get_sequentials *count*]
sim_save_reset
```

### 1.25 `sim_force`：在初始化仿真中强制信号

```text
sim_force <signal-name> -apply <value>
```

**参数解释。** 信号名是需要强制的对象，`-apply` 给出施加的值。这里展示的是复位仿真和初始化示例中的施加形式。

**用法与结果。** 强制初始化信号与在正式分析中固定常量不是同一个操作。标准的 `create_reset` 会组合初始化强制和正式分析中的非复位常量行为；手工编写初始化序列时，需要明确每个阶段的信号值，不能假定施加动作已经建立了全部后续约束。

```tcl

sim_run 3 -clk clk
sim_save_reset
```

### 1.26 `sim_set_state`：设置寄存器和存储器的初始状态

```text
sim_set_state [-fsdb {<file> <instance> <time>}]
              [-uninit_script <file_name>] [-apply <0|1|x|z>]
              [-exact] [-regexp] [-all] [-uninitialized]
              [-readmemb {<file> <memory> [start_addr [end_addr]]}]
              [-readmemh {<file> <memory> [start_addr [end_addr]]}]
              [-exclude_package] [-top <instance_name>] [-xml <file_name>]
              [<sequential-patterns-or-collection>]
```

**参数解释。** `-apply` 直接设置状态值；位置参数用于选择时序对象，`-all` 选择全部状态，`-uninitialized` 只选择未初始化的对象，`-exact` 和 `-regexp` 改变名称匹配的方式。`-fsdb` 从指定实例、指定时间取状态；`-uninit_script` 输出 FSDB 中缺少的未初始化对象脚本。`-readmemb`、`-readmemh` 分别读取二进制、十六进制的存储器文件，可以指定地址范围。`-xml` 读取保存的初始状态，`-top` 限定加载实例，`-exclude_package` 排除工具包中的信号。

**用法与结果。** 应在初始化仿真完成后设置，并随后保存状态；如果先设置再运行复位仿真，手工值可能被覆盖。把一个实际未复位的寄存器设为 0，是缩小初始状态集合；把有确定初值的寄存器设成 X，则是初始状态抽象。两者对证明结论的影响不同，都需要有明确的目的和证据。

```tcl
sim_run -stable
sim_set_state {u_counter.count} -apply x
sim_save_reset

sim_set_state -xml reviewed_reset.xml
sim_save_reset
```

来源：User Guide，X-2025.06-SP1，第 141–145 页。

### 1.27 `sim_save_reset`：把当前状态保存为形式初始状态


**参数解释。** 无参数形式把当前初始化状态保存到任务对应的复位状态资料中。

**用法与结果。** `create_reset` 只定义复位行为，`sim_run` 计算初始化状态，只有这个命令才会把当前状态交给后续证明。复制任务或读入复位 XML 之后，同样需要明确当前任务采用的初始状态，避免误用其他运行遗留的值。


### 1.29 `fv_setup_config`：配置模型准备检查

```text

                [-severity <error|info|warning>]
                [-autorun <checkpoint>] [-disable] [-enable]
                [-list] [-verbosity <none|summary|verbose>]
```

**参数解释。** `-check` 支持 `clock`、`comb_loop`、`glitch`、`multi_driver`、`osc_loop`、`osc_seq`、`reset`。`-category` 取 `all`、`general` 或 `modport`；非 all 类别要求只指定一种检查，modport 对应多驱动检查。`-severity` 默认是 warning，设为 error 可以在检查违规时终止流程。`-autorun` 的检查点为 `design_load`；本版组合环的自动检查只在设计加载点执行。`-disable`、`-enable` 改变检查的启用情况，`-list` 查看配置，`-verbosity` 默认 summary。

## 2. 属性、约束与运行

### 2.1 `fvassert`：创建断言或改变已有属性的使用方式

```text
fvassert [<name>] -expr {<property-expression>} [-clock <clock>]
fvassert [-class <classes>] [-type <types>] [-usage <usages>]
         [-filter <expression>] <property-names-or-collection>
```

**参数解释。** 带 `-expr` 时创建脚本属性；不带 `-expr`、直接传入已有属性名称时，则把它的使用方式设为 assert 并启用。`-class` 表示来源类别，`-type` 是声明或生成类型，`-usage` 是当前用途，三者不是同义词。

**用法与结果。** 表达式含显式采样事件时，就使用该事件；此时如果额外写 `-clock`，会给出警告并优先采用表达式中的时钟。没有事件时使用参考时钟。表达式用花括号保护，避免 `$past` 和位选择被 Tcl 解释。把假设转成断言是验证环境做出承诺的方法之一，但必须在承担该承诺的设计范围内加以证明。

```tcl
fvassert AP_HOLD -expr {
  @(posedge clk) disable iff (!rst_n)
  valid && !ready |=> valid && $stable(data)
}
fvassert assume_input_protocol
```

来源：User Guide，X-2025.06-SP1，第 87–89、106–113 页。

### 2.2 `fvassume`：创建环境前提或改变属性用途

```text
fvassume [<name>] -expr {<expression>} [-clock <clock>]
fvassume [<name>] -expr {<combinational-expression>} -depth <n>
fvassume [<name>] -env -expr {<environment-expression>}
fvassume <property-names-or-collection>
```

**参数解释。** 普通的 `-expr` 创建证明过程中的假设。`-depth n` 要求为正整数，只在复位后的前 n 个采样周期施加，默认以参考时钟的上升沿计数，可以用 `-clock` 改变；其表达式必须是组合逻辑，不能包含 SVA 时序运算符。`-env` 创建同时参与初始化和正式分析的环境约束，表达式只允许涉及主输入、未驱动网络、截断点和黑盒输出等指定对象，而且复位仿真所能接受的表达式还有额外限制。

**用法与结果。** `-env` 必须在 `sim_run` 之前建立，否则对已经完成的初始化不生效。假设应表达外部环境确实保证的条件；在同一个任务中把待证明的设计输出直接设成假设，就等于把问题本身删掉了。已证明断言的复用必须说明证明依赖，不能形成循环。

```tcl
fvassume AS_INPUT_STABLE -expr {
  @(posedge clk) disable iff (!rst_n)
  valid && !ready |=> valid && $stable(data)
}
fvassume AS_BOOT_MODE -expr {mode == 2'b00} -depth 3
fvassume AS_NO_TEST -env -expr {test_mode == 1'b0}
```

来源：User Guide，X-2025.06-SP1，第 66–76、87–89、106–113 页。

### 2.3 `fvcover`：创建可达性目标并扩展到事务结束

```text
fvcover [<name>] -expr {<sequence-or-expression>}
fvcover -extend_cond {<end-condition>} [-suffix <suffix>]
        <base-cover-property>
fvcover [-usage cover] [-class <class>] [-type <type>]
        -extend_cond {<end-condition>} [-suffix <suffix>]
```

**参数解释。** `-expr` 创建要寻找见证的目标。`-extend_cond` 基于已有覆盖追加布尔的结束条件，不能与 `-expr` 同时使用；`-suffix` 指定新名字的后缀，省略时追加 `_extended`。也可以按 source、script、covergroup 等属性类别或类型选择基础覆盖。

**用法与结果。** 到达一个覆盖点，并不等于事务已经正常退出。扩展覆盖要求该点之后还能到达空闲或事务清空的条件，适合检查“触发以后是否仍能完成”。它本质上仍在寻找一条轨迹，并不能自动证明所有命中该点的轨迹都能完成。

```tcl
fvcover CP_REQUEST -expr {@(posedge clk) req}
fvcover CP_TRANSFER -expr {@(posedge clk) req ##[1:4] ack}
fvcover -extend_cond {idle} -suffix eot CP_TRANSFER
```

来源：User Guide，X-2025.06-SP1，第 87–89、108–110 页。

### 2.4 `fvdisable`：停用选定的断言、假设或覆盖

```text
fvdisable [-class <classes>] [-type <types>] [-usage <usages>]
          [-filter <expression>] [<properties>]
```

**参数解释。** 可以按来源、声明类型、当前用途或名称选择属性；如果不明确区分筛选条件，容易影响到错误的对象。`-usage assume` 选择的是当前参与约束的属性，而不是所有原始声明为 assume 的属性。

**用法与结果。** 停用断言只是不再检查该断言，停用假设则会放宽允许行为，使已有证明资料失效，或者需要重新求解。User Guide 对 enabled 和 usage 的部分旧例描述并不一致，脚本应查询这两个属性，而不要依赖旧输出中的 none 文本。

```tcl
fvdisable -class aep -type bounds_check
fvdisable -usage cover
report_fv -list
```

来源：User Guide，X-2025.06-SP1，第 106–113、375 页。

### 2.5 `fvenable`：重新启用已有属性

```text
fvenable [-class <classes>] [-type <types>] [-usage <usages>]
```

**参数解释。** 按选择条件启用已有的目标，不会重新生成 RTL 中未插入的检查。

### 2.6 `fvdelete`：删除脚本属性

```text
fvdelete <property-names-or-collection>
```

**参数解释。** 指定要删除的属性对象。快速参考把这个命令列为属性管理操作，示例用于可由脚本重新建立的属性。

**用法与结果。** 删除会失去对象本身，停用则会保留对象和便于审计的信息。临时试验可以删除脚本目标；正式工程更应修改版本受控的属性源码和生成脚本，而不是只在交互会话里删除失败目标。

### 2.7 `get_props`：按类型、用途和状态查询属性集合

```text
get_props [-class <classes>] [-type <types>] [-usage <usages>]
          [-status <statuses>] [-filter <expression>]
          [-regexp] [-exact] [-selected] [<names-or-patterns>]
```

**参数解释。** `-class` 包括 source、script、aep、connection、coverage、register、security、seq、xprop、fusa 等来源；`-type` 描述具体的种类；`-usage` 取 assert、assume、cover。`-status` 按报告状态筛选，`-filter` 根据属性表达式筛选，`-regexp` 和 `-exact` 调整匹配规则；`-selected` 只取界面上当前选择的属性。

**用法与结果。** 返回的是工具集合。空集合可能是名称错误、没有生成目标、筛选条件错误或者属性被停用，不能直接解释为所有目标都已经通过。应查询集合大小，并结合未筛选的总报告来看。

```tcl
set asserts [get_props -usage assert]
puts "Assertions: [sizeof_collection $asserts]"
foreach_in_collection p $asserts {
    puts "[get_object_name $p] [get_attribute $p status]"
}
```

来源：User Guide，X-2025.06-SP1，第 110–114 页。

### 2.8 `check_fv`：证明属性或寻找覆盖见证

```text
check_fv [-block] [-run_finish <commands>] [-stop]
         [-break <number-of-falsifications>]
         [-property <properties-or-collection>]
         [-subtype <property|vacuity|witness>] [-assume]
```

**参数解释。** `-block` 阻塞直到本次检查结束；默认是非阻塞。`-run_finish` 指定非阻塞完成后执行的 Tcl 命令。`-stop` 停止当前运行，`-break` 在达到指定失败数时停止。`-property` 选择目标；`-subtype` 可以取一个或多个 property、vacuity、witness。`-assume` 允许把已证明的断言和不可达的覆盖用于约束。

**用法与结果。** 证明会同时服从启用的假设、常量、初始状态、黑盒和截断设置。非阻塞运行期间可以查看报告，但不能同时改变会影响运行的设置。完成意味着这次受资源限制的运行已经结束，并不等于全部目标都获得了确定结果；因此报告中的未完成状态必须单独处理。

```tcl
check_fv_setup -block
check_fv -block
report_fv -list > results.txt

check_fv -property [get_props AP_HOLD] \
    -subtype {property vacuity} \
    -run_finish {report_fv -verbose > hold_results.txt}
```

来源：User Guide，X-2025.06-SP1，第 184–189、202–207 页。

### 2.9 `report_fv`：读取证明状态、深度和详细结果

```text
report_fv [-class <classes>] [-type <types>] [-usage <usages>]
          [-status <statuses>] [-list] [-verbose] [-no_summary]
          [<property-names-or-patterns>]
```

**参数解释。** `-list` 输出逐项列表，`-verbose` 增加引擎、用时、证明深度和属性等详细信息，`-no_summary` 省略汇总。筛选参数只限定报告的对象，不会运行目标或改变其状态。

**用法与结果。** 报告是当前状态的快照。安全深度表示有界检查已经覆盖的范围，并不是无界证明；反例深度表示失败的位置，两者不能合并比较。筛选后如果只看到 proven 目标，必须另外查询总目标数以及其他状态，防止通过筛选制造出“全部通过”的假象。

```tcl
report_fv
report_fv -list -status falsified > failures.txt
report_fv -verbose -no_summary AP_HOLD
```

### 2.11 `set_grid_usage`：配置并行工作进程与计算集群

```text
set_grid_usage [-type <string>] [-control <string>] [-dir <string>]
  [-file <string>] [-memory <string>] [-global] [-default]
  [-job_array] [-prefetch_pct <percent>] [-level <integer>] [-navigator]
```

**参数解释。** `-type` 指定计算集群的类型及工作进程数，例如 `LSF=8`、`SLURM=6`；`-control` 是该集群实际使用的提交命令及资源要求。`-dir` 指定工作进程的临时目录，`-file` 指定提交配置文件。`-memory` 表示多级资源配置对应的内存容量（GB），`-level` 指定级别，必须从 0 开始连续编号。`-global` 作用于全部当前任务，`-navigator` 作用于 navigator 任务而不是普通的当前任务；`-default` 恢复默认设置。`-job_array` 启用作业数组，`-prefetch_pct` 控制预取进程的比例，范围为 0–100。

**用法与结果。** 请求的工作进程数并不等于实际获得的资源，也不是线程数或总内存。各个节点必须能访问相同的设计、临时目录和授权服务；队列的内存限制与形式引擎的内存限制应保持一致。提交字符串属于集群特定的配置，不能直接照搬其他站点的名称。

```tcl

```

### 2.14 `report_fml_engines`：按目标报告求解引擎表现

```text

                   [-depthCounts] [-depthVsTime]
                   [-status <statuses>] [-jobId <number>]
                   [-goalId <number>] [-engine <name>]
                   [-subtype <subtypes>] [-jobStatus <statuses>]
```

**参数解释。** 默认汇总当前任务最近一次的运行。`-list` 每个目标一行，`-verbose` 把每个目标在不同引擎中的状态分别列出。`-depthCounts` 按失败深度和有界深度计数，`-depthVsTime` 查看深度随时间的变化。`-jobId`、`-goalId`、`-engine`、`-subtype`、`-jobStatus` 分别按作业、目标、引擎、目标子类和作业状态筛选。

**用法与结果。** 一个属性可能产生自身、空洞性和见证等多个目标。报告中的累计引擎时间并不是墙上时钟的实际经过时间；SEQ 子证明的时间也可能是多个引擎的总和。判断性能改动时，应同时记录端到端时间、完成的目标数和安全深度。

### 2.15 `report_fml_jobs`：按作业报告运行状态与结束原因

```text
report_fml_jobs [-status <status>] [-reason <reason>] [-list]
                [-totaltime] [-no_summary] [-engine <name>]
                [-host <name>] [-jobId <integer>] [-profile]
                [-memBucket <GB>] [-grid_level <integer>]
```

**参数解释。** `-status` 筛选 scheduled、running 或 completed；`-reason` 筛选 normal、timeout、memout、orc_killed、sig_killed、crash、start_fail、misc_error 等原因。`-list` 列出每个作业的状态、时间、CPU 利用率、内存、目标数量和机器信息；`-totaltime` 汇总作业时间，`-no_summary` 省略汇总。`-engine`、`-host`、`-jobId` 按对象过滤；`-profile` 按引擎统计时间、内存和完成的目标，`-memBucket` 控制内存分组的宽度，默认 8 GB；`-grid_level` 筛选资源级别。

**用法与结果。** timeout 可能只是工具分阶段尝试短时引擎的正常结果；orc_killed 通常表示其他引擎已经解决了目标；sig_killed 可能来自集群外部的限制。它们都不能直接等同于 RTL 错误。CPU 利用率明显低于预期时，应先检查机器的争用情况和资源分配。

```tcl
report_fml_jobs -list
report_fml_jobs -reason memout -list
report_fml_jobs -profile -memBucket 4
```

来源：User Guide，X-2025.06-SP1，第 212–217 页。

### 2.16 `fvtask`：创建、切换和删除验证任务

```text
fvtask [-create] [-delete] [-limit_copy] [-copy <copy_task>]
  [-appcopy <app_name>] [-attributes <name/value-pairs>]
  [-asserts <properties>] [-assumes <properties>] [-covers <properties>]
  [-constants <signals>] [-snips <signals>] [-changeats <signals>]
  [-keep_status] [-keep_task] [<task_name>]
```

**参数解释。** `-create` 创建任务，并通常切换为当前任务；`-delete` 删除非默认任务；只给任务名表示切换任务。`-copy` 从指定任务复制，`-appcopy` 从指定应用复制。`-asserts`、`-assumes`、`-covers` 选择属性；`-constants`、`-snips`、`-changeats` 选择现有的常量、截断信号和变化时刻约束。`-limit_copy` 限制复制范围，要求至少指定一类属性；`-attributes` 显式指定任务的属性名和值。`-keep_status` 保留父任务的目标状态；`-keep_task` 创建或修改目标任务，但不切换当前任务。

**用法与结果。** 任务隔离允许按功能和难度组织证明，但不会自动使任务之间的假设变得正确。限制复制时，要特别检查约束、初始状态以及任务专属属性，User Guide 明确提示专属属性不会总是默认复制。新任务缺少关键的环境约束，可能出现伪反例；多复制了错误的假设，则可能导致不真实的通过。 时钟与复位定义是全局设置，不会因为拆成任务就形成独立的时钟环境。同一会话同一时刻只有一个任务执行 `check_fv`。语法定义中没有单列 `-abstractions`，即使说明文字提到复制抽象，也不应据此构造不存在于语法框中的开关。

```tcl
fvtask -create hold_checks -copy FPV \
    -asserts *hold* -assumes *
check_fv -block
report_fv -list
fvtask FPV
```

## 3. AEP

### 3.1 `aep_config`：在读入设计前控制自动检查生成

```text
aep_config [-dont_generate] [-type <type-list>]
           [-enable_counter_arith_oflow <true|false>]
           [-generate_only_with_fanout <true|false>]
           [<signal-name:state>]
```

**参数解释。** `-dont_generate` 阻止所选类别生成；`-type` 可以选择数组越界、算术溢出、驱动冲突、悬空、多驱动、分支完整性或互斥、置位复位、X 赋值、三种状态机锁定检查以及 all。位置参数可以精确到状态寄存器及其中某个状态，使用单个冒号连接。`-enable_counter_arith_oflow` 控制自增、自减计数器的算术溢出检查，默认 true；`-generate_only_with_fanout` 只保留目标信号有扇出使用的检查，默认 false。

**用法与结果。** 这个命令必须在 `read_file` 之前执行。它会改变插入到模型中的目标，而 `fvdisable` 只停用已经生成的目标。对于设计本来就允许等待的 RESET 状态，应按规格局部排除，不应把全部死锁检查关闭。User Guide 语法注释中提到的 `-exclude` 与展示的选项不一致，示例采用正文明确给出的 `-dont_generate`。

```tcl
set_fml_appmode AEP
aep_config -dont_generate -type fsm_deadlock \
    {u_ctrl.state:RESET}
aep_config -enable_counter_arith_oflow false
read_file -top ctrl -format sverilog \
    -aep bounds_check+fsm_deadlock -vcs {ctrl.sv}
```

来源：User Guide，X-2025.06-SP1，第 375–377 页。

### 3.2 `aep_generate`：生成状态机公平性及输入变化约束

```text
aep_generate -type <fsm_fairness|change_at>
             [-input_type <in|snip|abstract|bbout>]
             [-inputs <inputs-or-collection>] [-tcl <file_name>]
             [-max_width <integer>] [-bit] [-property <properties>]
```

**参数解释。** `-type fsm_fairness` 为相关输入建立公平性前提；`change_at` 建立允许变化的边沿规则。`-input_type` 指定主输入、截断点、抽象点或黑盒输出；`-inputs` 指定对象，不给时使用属性影响范围内的输入。`-tcl` 把生成结果写到文件以供审核。`-max_width` 限制总线位宽：未指定 inputs 时默认阈值为 2，指定 inputs 时默认为 10；超限会给出警告，没有生成任何公平性约束则会报错。`-bit` 按位生成，`-property` 限定相关属性。

**用法与结果。** 先建立时钟、复位和常量，再进行生成。总线公平性可能要求遍历其全部可能值，按位公平性也与总线的组合公平性不同；这些都是额外的环境承诺。建议先输出 Tcl，逐条确认外部环境真的保证这种变化，之后才 `source`。不能用公平性去强迫设计内部卡住的状态“总会变化”。

```tcl
create_clock clk -period 100
create_reset rst_n -sense low
aep_generate -type fsm_fairness \
    -inputs {ready response_valid} -max_width 2 \
    -tcl fairness_review.tcl
```

来源：User Guide，X-2025.06-SP1，第 377–380 页。

### 3.3 `enable_aep_goals_in_coi`：只启用指定 FPV 目标相关的 AEP

```text
enable_aep_goals_in_coi [-type <types>] [-status <statuses>]
                        [-filter <expression>] [-regexp] [-exact]
                        [<names-ids-or-property-collections>]
```

**参数解释。** 位置参数指定 FPV 目标；`-type` 限制 AEP 类别，`-status` 限定状态，`-filter` 施加属性过滤，`-regexp` 或 `-exact` 改变名称匹配的方式。

**用法与结果。** 这个命令在 FPV 应用中工作，会启用所选目标影响范围内的 AEP，并停用其他的 AEP。它用于聚焦相关的结构，并不等于其他结构已经验证过。使用后应记录 AEP 的总数和启用数量，避免在汇总报告中忽略未检查的部分。

### 3.5 `fvunwaive`：撤销目标豁免


**参数解释。** 指定已经有豁免的目标名称。

## 4. FXP

### 4.1 `fxp_generate`：按实例范围和类别生成 X 检查

```text
fxp_generate [<instance-scopes>] [-name <prefix>]
             [-type <type-list>]
```

**参数解释。** 范围使用实例名，而不是模块定义名；嵌套实例使用相对顶层的层级路径，多个实例写入 Tcl 列表。`-name` 作为生成属性的共同前缀。`-type` 选择来源和观察类别，省略时使用默认组合；auto 对应文档列出的默认组合。常见类别包括 uninit、oba、xassign、undef、undriven、in、out、bbin、bbout、unresin、unresout、abs 和 snip。

**用法与结果。** 默认类别并不是“给所有输入都注入 X”：主输入 in、黑盒输出 bbout 和未解析模块输出 unresout 在属性类型表中都不是默认项。语法列表中的 snipdrv 与表中的 snip_drv 拼写存在差异，教程不会把其中任意一个扩展成通用的可运行选项。最小案例显式给出 uninit 和 out，确保既有来源又有观察点。

```tcl
fxp_generate -name reset_x -type {uninit out}
fxp_generate {u_cpu u_uart.regs} \
    -name io_x -type {uninit xassign out}
report_fv -class xprop -list
```

来源：User Guide，X-2025.06-SP1，第 447–451 页。

### 4.2 `fxp_assume`：控制 X 来源或排除已知确定的位置

```text
fxp_assume -injectx [-name <name>] [-reset] [-oba] [-xassign]
           [-undef] [-condition <expression>] [-scope <scope>] <signal>
fxp_assume -nox [-name <name>] [-reset] [-condition <expression>] <signal>
```

**参数解释。** `-injectx` 建立 X 来源，`-nox` 从指定点排除 X。`-name` 为生成的目标命名；`-reset` 用于时序单元的出复位状态。`-oba`、`-xassign`、`-undef` 分别对应越界、显式 X 和未定义行为，作用于整个范围时必须配合 `-scope`；`-condition` 是控制该操作的组合条件。

**用法与结果。** 已经用 `create_clock` 或 `create_reset` 定义的时钟、复位信号不能作为 X 注入源。`-nox` 是模型前提，不会给 RTL 添加复位或屏蔽逻辑；只在规格或外部电路确实保证确定时使用。User Guide 的 nox 语法行漏写了 condition 前的连字符，参数解释和快速参考都采用 `-condition`，这里采用后者，并保留这一差异说明。

```tcl
fxp_assume -injectx -name cold_data -reset {u_buf.data_q}
fxp_assume -nox -name known_mode -condition {cfg_valid} {mode}
fxp_assert -name output_defined -condition {out_valid} {out_data}
```

### 4.3 `fxp_assert`：定义条件化的 X 观察点

```text
fxp_assert [-name <name>] [-condition <expression>] <signal>
```

**参数解释。** `-name` 指定检查名称，`-condition` 决定在哪些组合条件成立时要求目标信号确定；位置参数是观察信号。

**用法与结果。** 当无有效数据的周期允许数据寄存器未初始化时，应只在 out_valid 为真时要求数据确定。同时必须用 FPV 检查 out_valid 不会提前置位，否则错误的屏蔽条件可能让 FXP 看不到真实的问题。

```tcl
fxp_assert -name data_when_valid \
```

## 5. CC

### 5.1 `add_cc`：建立一条条件连通性检查

```text
add_cc -src <source-signals> -dest <destination-signals>
       [-enable <expression>] [-path_delay <min:max|latency>]
       [-enable_hold <cycles>] [-enable_delay <cycles>]
       [-offset_delay <cycles>] [-clock <clock-expression>]
       [-name <name>]
```

**参数解释。** `-src`、`-dest` 是有顺序的信号列表，支持名称模式，顺序决定对应关系。`-enable` 是连接成立的条件，默认 true；`-path_delay` 是源到目的的延迟，默认 0。`-enable_hold` 指定使能需要保持多久，`-enable_delay` 指定使能相对源值需要提前多久成立，默认都是 0。`-offset_delay` 指定复位后经过多少个周期才开始检查。`-clock` 给出采样表达式，默认使用已定义时钟的上升沿；`-name` 为检查命名。

**用法与结果。** 普通的同拍连接可以不含时序延迟；有延迟时必须有有效的时钟。源和目的名字正确，但顺序错误、位序颠倒或使能提前量不对，都可能造成失败。对于经过寄存器的路径，不能只通过增加 path_delay 随意消除反例，必须以接口的时序规格为依据。

```tcl
add_cc -name data0_to_y -src {a} -dest {y} -enable {!sel}
add_cc -name data1_to_y -src {b} -dest {y} -enable {sel}
check_fv -block
report_fv -class connection -list
```

来源：User Guide，X-2025.06-SP1，第 469–479 页。

### 5.2 `load_cc`：从 CSV 或表格式导入连接规格

```text
load_cc [-format <csv|table>] [-quiet] <filename>
        [-default_param_order]
```

**参数解释。** 默认格式是 csv；table 是工具定义的增强表格式，可以把使能条件分散在多列中。`-quiet` 抑制进度和结构检查的汇总，但仍会报告错误和警告。`-default_param_order` 让本次读取按默认字段顺序解释，不会覆盖已保存的自定义字段配置。

**用法与结果。** CSV 的列顺序是规格的一部分，不能只凭第一行的标题去猜工具的解释方式。table 格式需要两行表头，条件通常是多个位或字相等判断的合取，不能把任意的 SVA 写进表格里。导入后先看 `report_load_cc` 的成功条数和错误，再进行功能连通性证明。

```tcl
load_cc -format csv cc_connections.csv
report_load_cc -verbose
check_fv -block
```

来源：User Guide，X-2025.06-SP1，第 461–469 页。

### 5.3 `load_cc_set_param`：定义 CSV 字段的位置和组合方式

```text
load_cc_set_param <parameter-name> <value>
```

**参数解释。** 字段位置写成 `%1%`、`%2%` 等占位符，例如 csv_src、csv_dest、csv_prop_name、csv_enable。层级字段可以拼接，例如 `%3%.%4%`。csv_start_line、csv_end_line 用于行范围，csv_comment_pattern 指定行首的注释标志。其余的延迟、时钟和使能字段应与连接定义一致。

**用法与结果。** 列编号从 1 开始。拼接时空字段会被省略，相应多余的层级分隔符也会删除。它改变后续文件的解释规则，不会修改 CSV 本身；在同一个会话中导入多个不同格式的文件时，要显式切换配置或使用默认字段顺序选项。

```tcl
load_cc_set_param csv_prop_name "%1%"
load_cc_set_param csv_src "%2%"
load_cc_set_param csv_dest "%3%"
load_cc_set_param csv_enable "%4%"
load_cc_set_param csv_start_line "2"
load_cc cc_connections.csv
```

来源：User Guide，X-2025.06-SP1，第 464–468 页。

### 5.4 `report_load_cc`：报告连接规格导入和结构检查

```text
report_load_cc [-list] [-verbose] [-no_summary] [-error]

               [-not_applicable] [filename]
```

**参数解释。** `-list` 按文件列出每个目标的状态、行号和连接名；`-verbose` 还会显示详细信息；`-no_summary` 去掉汇总。其余状态选项分别筛选错误、警告、结构已连接、结构未连接和不适用的目标；位置上的文件名限制来源。

**用法与结果。** connected 在这个报告中是导入阶段的结构信息，并不是使能和延迟条件下的完整功能证明。not_applicable 可能来自被禁用或源为常量等情况，不能当成已通过。正式报告应同时包含导入条数和 `check_fv` 的结果。

```tcl
report_load_cc -error -verbose

report_load_cc -verbose cc_connections.csv
```

### 5.8 `generate_cc`：从设计提取可能的连接及使能条件

```text
generate_cc [-src <objects>] [-dest <objects>] [-control <objects>]
            [-run] [-preserve] [-clearall] [-file <path>]
            [-limit <integer>] [-verbose]
```

**参数解释。** 源、目的和控制对象可以是网络、端口或实例。先用 `-src`、`-dest` 积累对象对，再由 `-run` 执行提取。`-control` 指定使能表达式追溯到哪些控制对象；`-preserve` 保留源和目的供求后续运行使用，`-clearall` 清除已设置的源、目的和控制列表。`-file` 输出 Tcl，否则写入属性数据库；`-limit` 限制每对对象提取路径的数量，默认 1；`-verbose` 输出细节。

**用法与结果。** 提取的是当前 RTL 中已经存在的连接，并不是独立的规格。它适合辅助生成待审核的连接清单，但不能把由错误 RTL 自己提取的连接再证明一遍，就称为满足原设计需求。多对对象一次运行，通常比逐对运行更高效。

```tcl
generate_cc -src {a} -dest {y}
generate_cc -src {b} -dest {y}
generate_cc -run -file extracted_connections.tcl
```

```text
               [-run_finish <commands>] [-enable]
```

**参数解释。** `-par_task` 指定父 CC 任务，默认是当前任务；`-endpoint` 计算源和目的的翻转，`-net` 计算路径上的网络，`-enable` 包含使能表达式及其到选择位置的路径。`-property` 指定已启用且已证明的连接。`-structural` 直接把证明连接对应的覆盖目标标为已覆盖，不执行覆盖分析。`-block` 等待完成；本页对 `-run_finish` 写有只在阻塞模式下有效的限制，不能套用 check_fv 的非阻塞回调规则。

**用法与结果。** 必须在读设计时生成翻转目标，并启用连通性覆盖流程。`-structural` 的直接标记与实际翻转可达性的证明不是同一种证据；报告中必须加以区分。库文件缺省时可能不生成覆盖，需要根据工程使用 `-cm_libs vy`。

### 6.2 `save_cov_exclusion`：导出覆盖排除文件

```text
save_cov_exclusion -file <filename> [-append] [-missing_else]
  [-cov <metric_list>] [-line_intent] [-no_line_intent]
  [-filter <expression>] [-targets <goals>]
  [-enable_top_mod_excl] [-mod_excl] [-mod_excl_scope <modules>]
  [-strict] [-scope <module_or_instance>]
```

**参数解释。** `-file` 指定文件，`-append` 追加。`-missing_else` 纳入隐含的缺失 else 分支。`-cov` 以加号连接指标，支持 line、cond、toggle、fsm_state、fsm_trans、branch、cg、assert、cover、all；all 指结构覆盖类型，assert 和 cover 应显式指定。语法把 `-cov` 标为可选，但原文同一段又出现“mandatory”，与其省略该选项的示例相矛盾，正文采用其明确给出的省略示例，不把该句解释为必填。

`-line_intent` 只保留与代码意图相关的目标，`-no_line_intent` 排除这些目标；`-filter` 按属性筛选，`-targets` 显式指定目标集合。`-enable_top_mod_excl` 对顶层使用模块排除、对子层使用实例排除；`-mod_excl` 求同一模块各实例共有的不可达项，`-mod_excl_scope` 限定模块。`-scope` 限定导出的层次。`-strict` 写出供 URG/Verdi 严格检查使用的排除文件，以便发现“数据库中已覆盖、排除文件却排除”的冲突。

**用法与结果。** 默认导出已经判为不可达的目标，成功返回 1，失败返回 0。显式 `-targets` 可以改变导出的对象，因此仅有排除文件并不等于每一项都有不可达证明；审查时应同时保留约束、状态和日志。

```tcl
check_fv -block
save_cov_exclusion -file unr.el -strict
save_cov_exclusion -file selected_unr.el \
  -targets [get_props -status uncoverable]
```

### 6.3 `save_covdb`：保存形式覆盖分析结果

```text
save_covdb -name <covdb_name> [-update] [-overwrite]
  [-cov <metric_list>] [-line_intent] [-no_line_intent]
  [-status <status_list>]
```

**参数解释。** `-name` 给出目标数据库；`-update` 把结果作为新测试更新已有数据库，`-overwrite` 删除旧内容并重建，两种策略不要混用。`-cov` 筛选指标，`-line_intent` 与 `-no_line_intent` 筛选与代码意图相关的目标。`-status` 支持 covered、uncoverable。assert 和 cover 不会因为省略 `-cov` 就自动全部保存，需要明确选择。

### 7.2 `map_by_name`：按名称建立两侧对应关系

```text
map_by_name [-exclude <signals>] [-blackbox] [-undriven] [-abstraction]
  [-infer_unresolved_ports] [-map_type <types>]
  [-align_mismatch_bitwidth <alignment>] [-clock <clock>]
  [-edge <posedge|negedge|edge>]
  [-spec_latency <cycles>] [-impl_latency <cycles>]
  [-condition <expression>]
```

**参数解释。** `-exclude` 排除不应自动对应的信号；`-blackbox` 包括同名黑盒和编译存储器抽象，默认还要求其底层模块名相同。`-undriven` 对应未驱动信号，`-abstraction` 对应抽象对象。`-map_type` 限制对象的类别，例如只比较 output。`-align_mismatch_bitwidth` 指定不同位宽按 lsb 或 msb 对齐，使用前应确认哪一部分具有规格意义。

`-clock` 与 `-edge` 决定比较的采样事件，默认边沿为 posedge。`-spec_latency`、`-impl_latency` 设置两侧的比较延迟；`-condition` 限定相等检查成立的条件。未解析模块的端口方向可以由 `-infer_unresolved_ports` 辅助推断。这里展开的是 User Guide 在使用章节中逐项说明的选项，不把它误标为独立平台命令参考的全部选项。

**用法与结果。** 应在 `sim_run` 之前建立对应关系。在初始化之后才执行可能报错；即使降低错误等级，生成的约束种类也可能从环境约束变成普通属性约束，初始状态因此不再等价。输入和黑盒输出之间的相等通常形成假设；输出和黑盒输入之间的相等则形成待证明的目标，两者不能混淆。

```tcl
seqmap -port spec.request impl.req
map_by_name -exclude {debug_out}
report_seq_mappings -list
# 输出存在明确的采样时钟时，可单独建立带延迟的检查。
map_by_name -map_type {output} -clock spec.clk \
  -spec_latency 3 -impl_latency 3
```

### 7.3 `seqmap`：增加人工指定的对应关系

```text
seqmap [-name <name>] [-port] [-exact] <spec_expression> <impl_expression>
```

**参数解释。** 两个位置参数可以是信号、实例或匹配表达式。实例形式会在两侧实例下按寄存器名称寻找对应；通配形式只接受符合类别和位宽规则的对象。`-name` 给这条规则命名，多对匹配会产生带序号的派生名称；名称不能重复。`-port` 用于端口对象，`-exact` 表示精确的信号对，而不是前缀搜索。

**用法与结果。** 寄存器匹配主要是为求解器提供提示，并不意味着在未经证明的情况下就把内部寄存器强制设成相等。端口对应则可以生成输入假设和输出断言，必须按接口规格审查。在默认的表达式匹配中，寄存器与未驱动信号不能跨类别对应。

```tcl
seqmap -name state_pair -exact spec.state impl.state_reg
seqmap -port spec.req impl.request
map_by_name
report_seq_mappings -list
```

**参数解释。** `-specprefix`、`-implprefix` 默认是 spec、impl。`-recipe` 可以选 orch_generic_easy、orch_generic_low、orch_generic_medium、orch_generic_hard，默认 medium。`-map_uninit` 在复位时按名称对应未初始化的寄存器；`-map_counters` 对应抽象计数器；`-extended_mapping` 扩展人工对应的对象搜索范围。`-latch_scope` 选择对哪一侧进行锁存器处理。

### 8.1 `frv_load`：从寄存器规格生成并装入检查器

```text

  [-bind <bind_file>] [-top <[comp|mmap|block]:name>]
  [-checker_file <file>] [-include <type_list>]
  [-auto_load] [-parameters <parameter_list>] [-verbose]
```

**参数解释。** `-ipxact`、`-ral`、`-csv` 选择相应格式的寄存器规格，工程应明确选择自己的输入格式，不要把三种规格混在同一次调用中。`-bind` 给出总线连接文件；`-checker_file` 指定生成的检查器文件名，默认 frv.sv。`-top` 限定 component、memoryMap 或 addressBlock；不写类型时依次按 comp、mmap、block 查找，同名对象可以使用完整层次。

`-include` 可以选 unmapped、unmapped_reg、unmapped_field、reserved、reserved_reg、reserved_field。包含保留或未分配的空间之后，还需要设置 RSVD_MODE：0 不检查，1 期望全零，2 期望全一，3 使用 snps:outAddrValue 自定义值。`-auto_load` 装入生成的检查器、绑定文件和依赖库。`-parameters` 是 Tcl 参数列表，例如 `{RSVD_MODE=1 COVER_READ=1}`；支持的检查器参数还包括 ADDR_WIDTH、DATA_WIDTH、COMPOSITE、BUS_LATENCY、WR_LATENCY、RD_LATENCY、COVER_TYPE、COVER_WRITE、COVER_BYTE_UPDATE、OUTADDR_EN、LATENCY_MD、OUTABLK_MD、SNPS_AD_ABS、COVER_ALLOW_ERROR。`-verbose` 会显示不支持的结构，而不是静默忽略。

**用法与结果。** 这个命令生成检查器，但并不代表已经完成证明。总线封装必须把协议事件转换成检查器所需的读写事件；APB/AHB/AXI 封装在安装目录的 Frv 包中，其他协议需要检查并适配通用的封装。原文示例部分用 `-parameter`，正式语法用 `-parameters`，正文统一使用后者，不依赖工具对缩写的接受行为。

```tcl
frv_config -generate_covers true
frv_load -ipxact regs.xml -bind regs_bind.sv \
  -top block:soc.main.regs -include {reserved_field} \
  -parameters {RSVD_MODE=1 COVER_READ=1 COVER_WRITE=1} \
  -auto_load -verbose
frv_report
```

### 8.2 `frv_config`：控制寄存器属性生成范围

```text

  [-generate_covers <boolean>]
  [-generate_out_of_block_range_checks <true|false>:<0|1>]

  [-enable_volatile_check <none|with_hw_update|all>]
```

**参数解释。** 反向观察检查和 cover 生成默认开启；地址块之外的检查默认关闭。`-generate_out_of_block_range_checks` 同时给出开关及期望读值，期望值只能是 0 或 1，省略时默认 0。`-ignore` 当前列出 unknown_access；`-disable_backdoor_checks` 可以禁用寄存器数组或全部的反向观察检查。

`-generate_wo_read_check` 默认关闭，开启后再用 `-generate_wo_read_check_value` 指定只写字段被读时的期望值，顺序不能颠倒。`-generate_bdrsig_from_name` 根据规格的 name 属性生成 RTL 信号路径，只有当名称确实对应 RTL 时才可以使用。`-enable_fiv` 默认 false；`-enable_volatile_check` 默认 none，with_hw_update 只对带硬件更新描述的易变字段生成读数据检查，all 则对所有此类字段生成。

**用法与结果。** 必须在 `frv_load` 之前配置，因为这些选项决定生成哪些属性，而不是只在结果报告时进行过滤。无参数调用会打印当前的默认配置，适合保存到运行日志。boolean 选项按原文支持 true/false 或 1/0；对明确只列出 true/false 的选项，保持该拼写。

```tcl
frv_config -generate_covers true
frv_config -generate_wo_read_check true
frv_config -generate_wo_read_check_value 0
frv_config -enable_volatile_check with_hw_update
frv_config
frv_load -ipxact regs.xml -auto_load
```

来源：User Guide，X-2025.06-SP1，第 630–632 页。

### 8.3 `frv_report`：检查规格解析与属性生成情况

```text
frv_report [-hide_fields] [-no_summary]
  [-top <[comp|mmap|block]:name>]
  [-vendor_extensions <[comp|mmap|block]:hierarchical_name>]
  [-filter <expression>]
```

**参数解释。** `-hide_fields` 隐藏字段细节，`-no_summary` 隐藏汇总。`-top` 限定规格对象，类型省略时按 comp、mmap、block 查找。`-vendor_extensions` 展开指定寄存器或字段的厂商扩展信息。`-filter` 支持 regAccess、fieldAccess，用 `==` 或 `!=` 比较访问类型。

**用法与结果。** 应在证明前检查寄存器的数量、地址、属性数量与预期是否一致。缺少寄存器或字段检查，往往来自规格格式、访问类型、包含范围或参数设置，不能用“所有已生成断言通过”来掩盖漏生成的问题。

```tcl
frv_report
frv_report -filter {regAccess == rw}
frv_report -top block:soc.main.regs -hide_fields
frv_report -vendor_extensions block:soc.main.regs.CTRL.EN
```

来源：User Guide，X-2025.06-SP1，第 632–633 页。

### 9.3 `compute_fta`：执行形式测试环境质量分析

**参数解释。** `-par_task` 指明提供规格断言和约束的父任务。`-property` 可以显式选取用于检测故障的属性；省略时使用配置及默认的选择规则，通常为 proven 属性。

**用法与结果。** 先在全部故障被内部关闭的情况下重跑 FPV，确认注入后的设计模型仍满足原基线，再运行 FTA。故障未被检测，并不自动证明故障没有影响：可能是断言漏写、约束屏蔽了激活条件、故障不可传播，或者求解尚无结论。需要结合分类和反例继续分析。

## 10. FuSa

### 10.1 `fusa_config`：读取安全故障清单与数据库

```text
fusa_config [-sff <files>] [-fdb <database_name>]
  [-fdb_path <local_project_path>] [-fdb_server <server:port>]
  [-fdb_campaign <campaign>] [-status <statuses>]
  [-dut_path <dut_path>] [-save_fdb_incr <interval>]
```

**参数解释。** 至少要提供 `-sff` 或 `-fdb` 所代表的故障输入。`-sff` 接受 SFF 文件列表；`-fdb` 指定统一故障数据库。`-fdb_path` 是本地数据库路径，不能同时与 `-sff`、`-fdb_server` 使用；`-fdb_server` 选择服务端，`-fdb_campaign` 选择故障分析活动。`-status` 选择待分析的状态或状态组，状态组在 `fusa_generate` 时展开。`-dut_path` 对齐故障文件与当前设计的顶层路径。

`-save_fdb_incr` 控制运行期间的增量保存，单位为 M 或 H，默认 1H，非零时最小为 10M，设为 0 则关闭。SFF 流程重配之前需要 `fusa_clear`，并且 SFF 输入应在读设计之前完成。

**用法与结果。** 统一安全流程涉及的工具版本需要匹配。User Guide 的“本地 FDB”示意代码存在重复远程选项的排版问题，因此本教程以 `-fdb_path` 的明确定义来区分本地和服务端的用法。数据库可以连接，并不代表其故障对象都能在当前设计中找到，随后必须检查生成报告和忽略报告。

```tcl
set_fml_appmode FUSA
fusa_config -sff {faults.sff}
# FDB 工程可改用下面这一形式，而不是与上面的 SFF 调用连续混用。
# fusa_config -fdb safety_db -fdb_path /project/fdb \
#   -fdb_campaign main_campaign -dut_path controller
```

### 10.2 `fusa_clear`：清理本轮故障与生成属性

```text
fusa_clear
```

**参数解释。** 不带参数；清除已经读入的故障和相关属性，使后续可以重新配置。

**用法与结果。** FDB 流程可以在保留设计的情况下切换故障配置，但必须先 clear。更换 SFF 文件受读设计时机的限制：读设计之后再提供新的 SFF 会报错，旧式 SFF 流程在读设计之后甚至连 clear 也不允许。它并不是一条普遍适用的“任意重启本应用”的命令。

### 10.4 `fusa_blackbox`：为安全分析建立可传播的抽象模块

```text
fusa_blackbox [-module <modules>] [-all]
  [-all_auto_path] [-no_auto_path] [-seq_path] [-comb_path]
  [-ignore_unresolved] [-data_path_only] [-remove]
  [-task <failure_mode_task>] [<instances>]
```

**参数解释。** `-module` 或实例列表限定对象；`-all` 作用于全部结构黑盒。`-all_auto_path` 默认自动创建输入到输出的路径，`-no_auto_path` 则不自动创建；`-seq_path` 和 `-comb_path` 分别采用时序和组合传播。`-ignore_unresolved` 跳过未解析模块；`-data_path_only` 不沿多路选择器的选择控制传播，但允许数据分支传播。`-remove` 撤销安全抽象。`-task` 只在存在多个 failure mode 时指定所属任务。

**用法与结果。** 在设计展开之后、`fusa_generate` 之前使用。普通结构黑盒会断开传播路径，可能错误地证明故障不可观察；安全抽象则保持保守传播，但也可能添加实际上并不成立的路径，形成需要进一步精化的失败。生成之前的那份报告并不一定会列出最终的安全黑盒。

```tcl
fusa_blackbox -all -seq_path
fusa_generate
fusa_report -blackbox -path
```

### 10.7 `fusa_generate`：生成安全故障及分析属性

## 11. FSV

### 11.1 `fsv_generate`：定义禁止的信息传播

```text
fsv_generate -src <signals> [-src_condition <expression>]
  -dest <signals> [-dest_condition <expression>]
  [-exclude <signals_or_instances>] [-name <prefix>]
  [-zone <zone_name>] [-condition_cover]
```

**参数解释。** `-src`、`-dest` 必填，可为输入输出、寄存器、网络或实例；每个目的对象生成一个目标。`-src_condition` 只要求信息开始传播的那一拍成立；`-dest_condition` 只要求观察传播的那一拍成立，它们不要求同时或一直成立。`-exclude` 排除本条检查中的合法传播路径；`-name` 给属性和约束加前缀。`-zone` 将检查分组，同组源标记共同作用于该组断言，但单条源/目的条件不会自动共享。`-condition_cover` 增加条件覆盖检查，便于识别不可达条件。

**用法与结果。** 这个命令证明的是给定模型中不存在指定的传播，不是加密强度、所有侧信道或完整系统安全。把源条件换成始终成立的普通假设会改变问题，可能造成错误证明。时钟和复位不能作为普通标记源；被 create_clock/create_reset 声明的对象会被自动忽略并给出警告。

```tcl
fsv_generate -src {key_reg} -dest {debug_data} \
  -name key_to_debug -condition_cover
fsv_generate -src {secret_data} -src_condition {secure_mode} \
  -dest {public_data} -dest_condition {public_valid} \
  -exclude {u_encrypt} -name bypass_encrypt
```

来源：User Guide，X-2025.06-SP1，第 966–973 页。

### 11.2 `fsv_blackbox`：建立保持传播的安全抽象

```text
fsv_blackbox [-all] [-all_auto_path] [-no_auto_path]
  [-add_path] [-remove_path] [-src <input_ports>] [-dest <output_ports>]
  [-add_input_assertion] [-seq_path] [-comb_path]
  [-ignore_unresolved] [-data_path_only] [-remove] [<instance>]
```

**参数解释。** `-all` 处理全部结构黑盒；默认使用 `-all_auto_path` 自动建立路径；`-no_auto_path` 创建无自动路径的模型。`-add_path` 与 `-remove_path` 结合 `-src`、`-dest` 增减指定端口间的传播；`-add_input_assertion` 检查安全信息能否到达黑盒输入。`-seq_path` 引入一拍传播，有助于避免组合环；`-comb_path` 使用组合传播。`-ignore_unresolved` 跳过未解析模块，`-data_path_only` 限制控制选择信号的传播，`-remove` 撤销安全抽象。

**用法与结果。** 直接对有 RTL 的模块做安全抽象时，自动路径可以来自 RTL 的结构关系；先用结构黑盒删除内部逻辑，再加上安全抽象，就只能保守地连接所有输入与输出，可能造成更多失败。反过来，普通结构黑盒切断传播则可能造成错误的通过。人工删除路径必须有设计或规格依据。

```tcl
fsv_blackbox -seq_path -all_auto_path u_cipher_ctrl
fsv_report -blackbox -path
# 只有确认 ack_i 到 req_o 不存在功能传播时才移除该路径。
fsv_blackbox -remove_path -src ack_i -dest req_o u_cipher_ctrl
```

来源：User Guide，X-2025.06-SP1，第 978–982 页。

### 11.3 `fsv_report`：审查安全抽象及传播路径

```text
fsv_report -blackbox [-list] [-path_config] [-path] [-col]
```

**参数解释。** `-blackbox` 选择安全抽象报告，`-list` 列出对象，`-path_config` 显示用户配置，`-path` 展开当前的输入到输出路径，`-col` 返回实例集合。这里只列出 User Guide 对安全黑盒报告明确说明的形式。

**用法与结果。** 用户配置不等于最终的路径集合；自动建立路径和人工增删之后，应查看 `-path`。路径缺失会导致假通过，保守路径过多会导致假失败，二者的处理方向相反。

```tcl
fsv_report -blackbox -list
fsv_report -blackbox -path_config
fsv_report -blackbox -path
```

来源：User Guide，X-2025.06-SP1，第 981–982 页。

## 13. DPV

### 13.1 `create_design`：创建数据路径参考或实现设计

```text
create_design -name <design_name> -top <top_function_or_module>
              [-clock <clock_port>] [-reset <reset_port>] [-negReset]
```

**参数解释。** `-name` 建立后续编译引用的设计名，通常是 spec、impl；`-top` 对 C++ 是捕获封装函数，对 RTL 是模块。`-clock`、`-reset` 描述 RTL 端口；`-negReset` 表示低有效复位，省略时表示高有效。

**用法与结果。** 这是 DPV/HECTOR 的设计创建接口，不能用普通 `create_clock`、`create_reset` 的语法替代这些选项。C++ 封装必须通过 `Hector::registerInput`、`Hector::registerOutput` 和 capture 区间定义事务；只有普通 C++ 函数却没有声明输入输出，不能自动得到正确的比较问题。

```tcl
proc compile_spec {} {
  create_design -name spec -top hector_wrapper
  cppan spec.cc
  compile_design spec
}
proc compile_impl {} {
  create_design -name impl -top adder -clock clk -reset rst_n -negReset
  vcs impl.v
  compile_design impl
}
```

### 13.8 `DPV_map_by_name`：为 DPV 建立事务阶段对应


```tcl

```

### 13.9 `assume`：在 DPV 中声明输入关系或合法值

```text

```

**参数解释。** 名称用于标识假设，等号后是 HECTOR 表达式；`impl.in_a(1)` 表示实现设计中指定事务阶段的信号，不是普通的 SystemVerilog 函数调用。


### 13.10 `lemma`：在 DPV 中声明输出等价目标


**用法与结果。** 在输入对应和事务条件都已经建立之后，再证明 lemma。需要多个输出或多个操作模式时，应分别命名，有助于区分位宽、符号扩展、溢出和流水时刻的问题。


### 14.1 `fvtrace_config`：配置反例中不确定来源的检查

```text
fvtrace_config [-check <checks>] [-type <types>]
  [-autorun <checkpoint>] [-severity <severity>]
  [-verbosity <summary|verbose>] [-enable] [-disable]
```

**参数解释。** `-check` 选择 initialstate、undriven、aepnode、loop_cutpoint 等检查类别；`-type` 进一步选择子类，例如未初始化的 design/sampled、未驱动的 usersnip/userblackbox、未定义行为的 bound/explicitx/divbyzero。省略类别或子类时，选择适用的全部项。`-severity` 设置严重程度，`-verbosity` 控制输出的详略；`-enable`、`-disable` 控制指定的检查。

**用法与结果。** `-autorun` 在打开轨迹时自动检查，none 则关闭。原文定义提到 view_trace，示例却写成 viewtrace，存在拼写差异；为避免依赖该差异，以下示例使用显式的 `fvtrace_check`。这个分析会揭示反例依赖哪些不确定来源，但并不等于自动判定反例为设计错误。

```tcl
fvtrace_config -check initialstate -severity low -enable
fvtrace_config -check aepnode -severity high -enable
fvtrace_check p_data_correct
```

### 14.2 `fvtrace_check`：检查已有轨迹中的初始化与未定义行为

```text

              [-vacuity] [-witness] [-clear] [-quiet]
```

**参数解释。** 属性必须已经有可用的轨迹。`-check`、`-type` 限制检查范围，省略时使用已启用的类别；`-vacuity`、`-witness` 选择对应的辅助轨迹；`-clear` 清除该轨迹的分析结果；`-quiet` 抑制执行时的输出。

**用法与结果。** 未初始化的寄存器、被切断的驱动器、黑盒输出、数组越界和显式 X 都可能贡献自由选择。检查应围绕真正影响失败的来源进行，而不是一看到任何 X 就把反例忽略。

### 14.8 `report_fv_complexity`：分析影响属性的设计结构

```text
report_fv_complexity [-stopif <expression>] [-stops <objects>]
  [-list] [-verbose] [-col] [-limit <n>] [-level <n>] [-xml <file>]
  [-filter <expression>] [-regexp] [-nocase] [-bit]
  [-disable_abstraction] [-design] [-instrumented] [-include <types>]
  [-complement] [-property <properties>] [-output_mode <mapped|unmapped>]
  [-subtype <vacuity|property|witness|all>]
  [-usage <assert|assume|cover|all>] [<objects>]
```

**参数解释。** `-property` 或位置对象指定起点；多个起点按影响集合的并集统计。`-stops` 指定停止对象，`-stopif` 按属性表达式停止搜索。`-list` 展开对象，`-verbose` 增加位宽和源码位置，`-col` 返回集合；`-limit` 默认报告 100 项，-1 表示不限制，只作用于这些展开形式。`-level` 只用于按层次迭代的报告，不能与显式的起点混用。`-xml` 保存结构化报告，`-gui` 是原文另列的图形显示开关。

`-filter` 用于筛选，`-regexp` 和 `-nocase` 控制模式匹配。默认按字统计，`-bit` 更精确但更慢。`-design` 默认包含设计对象，`-instrumented` 包含工具插装对象，`-include` 可以纳入 leaf_module、constraint、latch_loop、combo_loop。`-complement` 查看影响范围之外的对象，`-disable_abstraction` 关闭复杂算子抽象以检查真实结构。`-output_mode` 仅适用于 SEQ；`-subtype` 默认 property，`-usage` 默认 all。

**用法与结果。** 影响范围大，说明证明可能困难，但它并不是证明所需逻辑的精确集合。结构识别依赖 RTL 和综合形式：门级搭出的加法器不一定被识别为加法算子。调优时应把复杂度与实际求解时间、深度和 formal core 一起看。

```tcl
report_fv_complexity -property p_data_correct -verbose -limit 100
report_fv_complexity -property p_data_correct -bit
report_fv_complexity -level 1 -xml complexity.xml
```

来源：User Guide，X-2025.06-SP1，第 719–734 页。

### 14.9 `get_fv_complexity`：返回影响范围中的结构集合


### 14.12 `set_abstractions`：用较简单模型代替复杂结构

```text
set_abstractions -construct <construct_thresholds>
  [-using <abstraction_model>] [-filter <expression>] [-remove] [-global]
```

**参数解释。** `-construct` 指定结构及尺寸阈值，例如 `{mult=8 div=8 count=8}`；常见的结构还包括 add、sub、mod、array、vector、array_comb、vector_comb。默认 snip 用自由变量代替复杂结果。`-using keyvals` 将计数器分成关键值区间；`+linearize` 保留递增/递减方向，在区间内仍允许跨步。可以增加用户关键值，或使用 user/range 的相关组合；具体组合以本章展示的支持形式为限。`-filter` 限定对象，`-remove` 撤销，`-global` 应用于所有任务。

**用法与结果。** 必须在读入设计之后使用，因此它主要改善形式模型和求解，并不减少 RTL 读入的时间。保守抽象会扩大行为集合：证明成功通常可以支持原问题，但失败可能是抽象引入的伪反例。添加约束精化抽象时，必须保证没有删除原设计的合法行为。

```tcl
set_abstractions -construct {mult=16}
set_abstractions -construct count=4 -using keyvals+linearize
report_abstractions -verbose
# 对照实验需要恢复时：
set_abstractions -construct {mult=16} -remove
```

来源：User Guide，X-2025.06-SP1，第 744–749 页。

### 14.13 `report_abstractions`：核查实际生效的抽象

**参数解释。** 无参数时汇总已抽象的结构数量；`-list` 给出结构、尺寸、模型和被驱动网络；`-verbose` 进一步列出输入、关键值等；`-construct` 只报告指定的类型与阈值。

**用法与结果。** 这个报告用于确认抽象是否真正命中目标结构。计数器位宽较小、结构未被识别或过滤名称不对，都可能使设置没有起到预期作用。返回 1 表示报告命令成功，并不是形式证明通过。

### 14.14 `compute_proof_assist`：定位证明代价随深度增长的原因

```text
compute_proof_assist [-block] [-stop] [-property <properties>]
  [-depth <n>] [-minimize <regs>] [-profiler <p0|p1>]
  [-ignore_status] [-live_update <core|depth|all>] [-config <settings>]
```

**参数解释。** `-property` 选择目标；`-depth` 默认 1000，通常需要目标已有至少一层检查结果，未完成或失败属性的所选深度应与已有结果相容。`-ignore_status` 允许不按原状态限制启动分析。`-minimize regs` 尝试减少核心寄存器；p0 收集核心、深度和时间，p1 还会收集求解工作量，并且是默认值。`-live_update` 选择实时更新的内容。`-config` 用 `{profiler=p1,depth=100}` 设置后续的默认值，空列表则查询当前值。

**用法与结果。** 这个功能在该版本明确支持 FPV 和 FRV。它是性能诊断，并不是把未完成属性直接转成证明；建议先看是哪一深度引入了存储器、长计数或昂贵的属性逻辑，再决定改写还是抽象。

### 14.15 `report_proof_assist`：解释性能分析与建议

```text
report_proof_assist [-xml] [-verbose] [-depth <n>]
  [-constraints] [-comb] [-bit] [-target <registers>] [-last_depth]
  [-top_signals <n>] [-last_cores <n>] [-explicit_cycles]
  [-property <property>] [-coi] [-note_truncation <on|off>]
  [-advisor] [-advisor_level <0|1|2|3>] [-report_cutoff <n>]
  [-engine <engine>] [-model <model>] [-intent <intent>]
  [-mode <mode>] [-config <settings>]
```

**参数解释。** `-depth`、`-last_depth`、`-last_cores` 限定深度或核心序列，`-explicit_cycles` 不合并相似的周期。`-constraints` 包含约束，`-comb` 包含组合逻辑，`-bit` 进行位级显示；`-target` 聚焦寄存器，`-top_signals` 和 `-report_cutoff` 限制显示数量。`-coi` 还会显示指定深度内不在核心中的影响对象。`-xml`、`-verbose` 控制输出的格式和细节。

`-advisor` 添加建议；`-note_truncation` 默认 on，按原文截到 80 字符。`-advisor_level` 是两位开关，最低位控制复杂度说明，第二位控制下一步的 Tcl 建议，默认 2。`-engine` 可以是 all、deepest 或 fc1–fc5，默认 deepest；`-model` 可以是 all、def、deepest 或模型名。`-intent` 可以是 bug-hunting、coverage、proof、all，默认 all；`-mode` 可以是 core-buildup 或 comparative。`-config` 支持相应的默认设置，空列表则只查询。

**用法与结果。** 最高代价信号只是候选原因。如果昂贵部分主要来自属性本身，应先检查不必要的深层 `$past`、复杂匹配或参考模型；如果来自真实数据通路，再考虑在保持规格正确性的前提下做拆分和抽象。不要未经复核就直接执行自动建议中的限制。

```tcl
report_proof_assist -last_depth -verbose -comb -constraints
report_proof_assist -advisor -advisor_level 3 -intent proof
report_proof_assist -mode comparative -depth 20 -engine all
```

### 15.1 `compute_formal_core`：计算某个证明使用的形式核心

```text
compute_formal_core [-block] [-stop] [-property <properties>]
  [-subtype <vacuity|witness>] [-depth <n>]
  [-goalIds <ids>] [-proof <proof_name>] [-minimize <regs>]
```

**参数解释。** `-property` 选择属性，`-subtype` 选择辅助组件，`-depth` 请求有界核心。`-goalIds` 与 `-proof` 只适用于 SEQ；`-minimize regs` 尝试减少寄存器，代价可能增加，不能理解为找到全局最小的核心。`-block` 等待完成，`-stop` 停止。

**用法与结果。** 核心必须与它支持的结果种类一起解释：完整证明核心、有界核心以及计算未完成，并不是同一种证据。这一章节对默认增量行为、无 `-depth` 时的状态选择和示例注释有不一致的叙述，因此批处理示例显式选择 proven 属性；分析有界结果时，显式给出深度并核对报告。

```tcl
compute_formal_core -property [get_props -status proven] -block
report_formal_core -union -verbose
```

### 15.2 `report_formal_core`：报告证明涉及和未涉及的设计对象

```text
report_formal_core [-subtype <subtypes>] [-property <properties>]
  [-list] [-no_summary] [-verbose] [-complement] [-union]
  [-runStatus <completed|scheduled>] [-status <proven|bounded|no_status>]
  [-exclude_constraints] [-goalIds <ids>] [-proof <proof_name>]
  [-comb] [-bit]
```

**参数解释。** `-union` 求所选属性核心的并集，`-complement` 查看其外部的对象；`-property` 限定属性。`-list`、`-verbose`、`-no_summary` 控制显示；`-runStatus` 筛选计算进度，`-status` 筛选核心的证据状态。`-exclude_constraints` 排除仅由约束贡献的寄存器/输入；SEQ 可以用 `-goalIds`、`-proof`。`-comb` 包含组合逻辑，`-bit` 按位统计，两者不应同时使用。

**用法与结果。** 环境约束与 `set_constant` 是隐式的背景，不会全部显式列出；加密区域的寄存器也不一定会显示。核心之外，不代表功能无需验证；核心之内，也不代表所有功能都已检查。位级与字级统计的分母不同，不能直接比较百分比。

```tcl
report_formal_core -union -verbose
report_formal_core -complement -verbose
report_formal_core -comb -union
```

### 15.4 `snip_formal_core_complement`：创建切断核心外部寄存器的诊断任务

```text
snip_formal_core_complement -property <property>
  [-par_task <parent_task>] [-new_task <new_task>]
```

**参数解释。** `-property` 必填，指定已有核心结果的目标；`-par_task` 指定父任务，`-new_task` 为新任务命名。

**用法与结果。** 它用于判断核心之外的大量状态是否拖慢了证明。切断会增加自由行为，出现的失败可能是伪反例；这个实验不能直接代替原模型的验收。应保留父任务不变，并审查新任务的抽象及结果传播关系。

```tcl

snip_formal_core_complement -property p_data_correct \
```

### 16.1 `fv_proof_arch`：创建、生成与审查分解证明策略

```text
fv_proof_arch -name <name> [-type <type>] [-subtype <subtype>]
  [-append] [-generate] [-property <properties>] [-assumes <properties>]
  [-ignore_status] [-unsafe] [-propagate <true|false>]
  [-distribute_max_tasks <n>] [-distribute_max_props <n>]
  [-distribute_custom] [-model_summary] [-model_ref <strategy>]
  [-audit] [-signal <signal>] [-values <values>] [-enumerate <mode>]
```

**参数解释。** `-name` 全局唯一且必填。`-type` 可以是 copy、assume_guarantee、abstraction、over_constraint、case_split。assume_guarantee 的 `-subtype` 可以是 acyclic（默认）、chain、grouped_induction；case_split 默认 subspace，event 另属该版本的 Beta 说明范围。`-append` 添加字段，`-generate` 根据当前的定义生成并锁定子任务；`-property` 选择待证明目标，`-assumes` 选择辅助假设。

**用法与结果。** 先设置 `fv_proof_architect true`。假设—保证分解不能让两个未独立成立的目标循环地互相假设；chain 中工具会禁止这种循环。抽象、增加限制和子空间分解有不同的结果传播规则，因此即使所有子任务都显示成功，仍需通过策略完整性审查。

```tcl

fv_proof_arch -name split_goals -type copy -distribute_max_props 20
fv_proof_arch -name split_goals -property [get_props -usage assert] -generate
fv_proof_arch_report -name split_goals
check_fv -proof_arch split_goals -block
fv_proof_arch -name split_goals -audit
```

来源：User Guide，X-2025.06-SP1，第 805–810 页。

### 18.18 `copy_collection`：复制集合容器


**参数解释。** 返回独立的集合副本。副本中的成员仍是同一设计中的对象，不会复制实例、引脚或网络。

**用法与结果。** 普通的 `set b $a` 复制的是集合句柄的引用。这个命令适合明确要求独立集合容器的场合，但不应误认为复制之后就拥有第二份可以独立修改的 RTL 设计。

```tcl
set original [get_cells *]
set snapshot [copy_collection $original]
puts [sizeof_collection $snapshot]
```

来源：User Guide，X-2025.06-SP1，第 1099 页。

### 18.19 `index_collection`：按下标取得集合成员

```text
index_collection <collection> <index>
```

**参数解释。** `<index>` 从 0 开始。返回指定位置的对象集合。并不是所有集合都支持按下标访问，应优先使用集合遍历。

**用法与结果。** 按位置选择对象，通常不如按准确名称或属性可靠；展开或排序的变化可能改变对象顺序。确实需要选择第一项时，先检查集合非空，并在报告中打印选中对象的名称。

```tcl
set ports [sort_collection [get_ports *] full_name]
if {[sizeof_collection $ports] > 0} {
    puts [get_object_name [index_collection $ports 0]]
}
```

来源：User Guide，X-2025.06-SP1，第 1099 页。

### 18.20 `get_attribute`：读取对象属性

```text
get_attribute <object> <attribute>
```

**参数解释。** `<object>` 是要查询的对象，`<attribute>` 是大小写敏感的属性名。常见属性包括 `object_class`、`full_name`、`direction`、`ref_name` 和 `is_sequential`，但并不是每类对象都支持全部属性。

**用法与结果。** 对象属性描述当前展开的模型，不应脱离对象类别来解释。例如实例的 `ref_name` 是它所引用的设计或库单元，端口的 `direction` 描述顶层接口方向。应用属性通常是只读的，不应尝试通过改属性来代替修改 RTL 或设置验证环境。

```tcl
foreach_in_collection p [get_ports *] {
    puts "[get_attribute $p full_name] : [get_attribute $p direction]"
}
```

来源：User Guide，X-2025.06-SP1，第 1100–1105 页。

### 18.21 `list_attributes`：列出某类对象可查询的属性

```text
list_attributes -application -class <class>
```

**参数解释。** `-application` 包含工具应用定义的属性；`-class` 指定对象类别，例如 `cell`、`port`、`pin`、`net`、`design`、`lib_cell`、`lib_pin`。

**用法与结果。** 先查看属性目录，再编写筛选表达式，可以避免把其他工具或其他类别的属性直接套用过来。目录给出属性名和类型；具体对象是否具备某项属性，还应结合该对象的实际查询结果来判断。

```tcl
list_attributes -application -class cell
list_attributes -application -class port
```

来源：User Guide，X-2025.06-SP1，第 1100–1101 页。
