# 反例调试、证明性能与复杂性控制

## 1. 为什么形式验证会困难

大设计的原始状态空间往往呈指数增长。真正决定计算规模的不是 RTL 总行数，而是某一条属性需要考虑的状态、时钟、存储结构、算术逻辑、输入自由度和时间深度。极大规模的 SoC 中，一个受局部状态机约束的输出属性可能很容易，而一个 64 位除法运算或需要跨上千周期的罕见序列可能十分困难。

这意味着：**先理解问题与所需观察状态，再投入更多机器资源。**

![失败、空洞与未完成的分流](插图/15_调试决策.svg)

## 2. 报告状态决定不同的调试路径

| 状态 | 首先需要回答的问题 | 典型措施 |
| --- | --- | --- |
| Falsified | 是否是真正可实现的反例 | 查看波形、复位、合法输入和抽象 |
| Proven | 规则是否完整且非空洞 | `cover` 触发、审查假设及性质范围 |
| Inconclusive | 计算难点在哪里 | 复杂性报告、拆分、抽象、策略调整 |
| Uncoverable | 目标为什么无法到达 | 审查环境约束与初始状态 |
| No properties | 属性是否编译和启用 | 检查 `-sva`、`bind`、模式和任务 |

先按结果类型分流，再决定是否调整资源。明确失败应先分析反例；空洞通过和约束冲突应先修正模型；只有在环境可信而目标仍未完成时，才进入复杂度、抽象和证明策略分析。对所有问题统一增加运行时间，既浪费资源，也可能延迟发现建模错误。

## 3. 失败属性：逐周期回溯

```tcl
report_fv -list
report_fv -verbose
view_trace -property <actual_property_name>
```

波形中应同时查看触发输入、内部状态、相关有效标志、输出及复位；不能只截取失败周期最后一帧。回溯时先从断言后件不满足的位置定位，然后反推输入是否启动了前件检查。许多“错误”属于 SVA 错把 `|=>` 写成 `|->`、忽略非阻塞赋值采样、没有在 `$past` 前验证历史有效等问题。

### 3.1 错误类型诊断表

| 典型反例 | 建议核查 |
| --- | --- |
| 复位刚释放就失败 | 复位模型、SVA 失效条件、前一拍采样 |
| 外部输入给出非法值 | 协议是否允许；合法约束是否缺失 |
| 某内部寄存器突然跳变 | 是否黑盒、抽象或部分初始状态任意 |
| 只有一条复杂断言失败 | 拆成数条检查以确定错误具体阶段 |
| 重试之后“失败消失” | 模型或约束是否变化，是否仅换了证明任务 |

调试应沿时间顺序定位第一次偏离规格的状态，而不是只看最后一拍断言变红。将导致该状态的输入、前一拍寄存器值、复位和使能条件同时展开，再判断错误属于 RTL、属性、环境还是抽象。修改时只改变已定位的原因，并保留原始反例用于回归。

## 4. 约束检查：最应优先防止的错误

形式环境常见问题是**过度约束**：为了让属性收敛，把本应由 DUT 产生的某个输出/内部状态假设为正确；或者把关键请求置为恒零，使断言从不触发。另一类是**约束不足**：允许非法输入状态，导致反例不符合系统协议。

对每个 assume 保存三个信息：自然语言前提、规格或接口出处、可以用于反驳不合理假设的覆盖目标。跨时钟约束尤其要区别输入保持、边沿采样和真实时钟独立性。若存在多组假设，可分组关闭并比较覆盖目标的可达性。

## 5. 查找状态空间问题

```tcl
report_fv_complexity
report_fml_engines
report_fml_jobs
report_fml_hosts
```

复杂性报告帮助识别大影响锥和特殊数据结构。面对大型存储器，可以考虑：将具体数据证明缩减为一个或少量符号地址、抽象未直接参与控制的 RAM 内容、将读写控制与数据正确性分别验证；但必须清楚抽象是否覆盖真实冲突规则和初始化语义。面对大型算术逻辑，可能需要拆分操作码、证明进位或截断的局部不变量。

## 6. 改善证明性能的合理顺序

1. 首先排除环境错误和空洞的属性。
2. 查找关键的状态和输入，拆分长时序规则。
3. 增加正确的辅助不变量，而不是任意假设结论。
4. 按功能建立独立任务 `fvtask`，先单独证明基础性质。
5. 选择合适的引擎努力程度与运行时间，例如 `set_fml_var fml_effort high`。
6. 对仍存在规模问题的属性评估抽象/分解；出现新反例时回原始设计验证其可行性。
7. 根据主机内存和许可证数配置网格，并对比实际加速效果。

## 7. `fvtask`：按性质组织工作

```tcl
fvtask -create reset_task
fvtask -create datapath_task
# 选择工作任务
fvtask reset_task
get_fvtask
```

不同应用对复制任务或传递属性集合的选项支持可能不同，实际可使用 `fvtask new_task -copy source_task` 或查看 `help fvtask`。为了便于回归，不应在不记录的情况下频繁切换任务并把不同任务的结果拼成一份“同一配置完成”的报告。

## 8. 抽象及裁剪驱动器

```tcl
# 进阶操作，仅在确认目标和影响后使用
snip_driver u_dut.internal_net
set_abstractions -construct {mult=16 count=4}
report_abstractions
```

裁剪部分网络的驱动或用抽象代替复杂数据结构后，原设计的行为集合可能改变。这可能加速求解，但也可能出现物理上不可能的反例或把某些条件与设计脱离。任何用于最终证明的抽象都需要解释其正确性及覆盖范围。

## 9. 困难证明的辅助分析

| 指令 | 说明 |
| --- | --- |
| `compute_reduced_constraints -property ...` | 分析对某条证明真正相关的约束子集 |
| `report_reduced_constraints` | 输出与证明有关的约束信息 |
| `compute_formal_core -property ...` | 分析证明关注的关键逻辑部分 |
| `report_formal_core` | 输出核心逻辑关系 |
| `compute_proof_assist -property ...` | 获取部分证明辅助信息 |
| `report_proof_assist` | 输出辅助结果 |
| `fvlearn_config -local_dir ...` | 按版本配置回归加速数据 |

这些是深入调优工具，而不是新手应默认启用的选项；应先明确每次调优对结果是否有实质影响。

## 10. Proof Architect：组合式证明思路

当一个大型属性难以一次性证明时，可以选择辅助不变量、局部切分和多阶段验证。组合式证明（Compositional Verification）思路是：将大问题分解成较容易的子目标，在逻辑上确保子目标联合能支持原结论。Proof Architect 是 VC Formal 提供的相关能力之一，详见 User Guide 第 19 章。

**正确分解需要保证：**局部证明使用的假设可由其他模块实际保证；模块间不会形成未经处理的循环假设；最终合成结论对应原始设计。这不是“把大模块拆成几份后，每份单独通过就自动保证整体”。

## 11. 有规律地建立证明性能实验

每次实验应只改变一到两个有解释的因素。保存：属性数量、最长/最难属性、证明状态分布、CPU 时间、总运行时间、峰值内存、worker 数、工具版本、输入哈希值。面对证明效率提升，要区分是确实证明了更多属性，还是把一部分属性禁用或过度约束造成的虚假改善。

### 12.1 `fvtrace_config`：配置反例中不确定来源的检查

```text
fvtrace_config [-check <checks>] [-type <types>]
  [-autorun <checkpoint>] [-severity <severity>]
  [-verbosity <summary|verbose>] [-enable] [-disable]
```

**参数解释。** `-check` 选择 initialstate、undriven、aepnode、loop_cutpoint 等检查类别；`-type` 进一步选择子类，例如未初始化的 design/sampled、未驱动的 usersnip/userblackbox、未定义行为的 bound/explicitx/divbyzero。省略类别或子类时选择适用的全部项。`-severity` 设置严重程度，`-verbosity` 控制输出详略；`-enable`、`-disable` 控制指定检查。

**用法与结果。** `-autorun` 在打开轨迹时自动检查，none 关闭。原文定义提到 view_trace，示例却写 viewtrace，存在拼写差异；为避免依赖该差异，以下示例使用显式 `fvtrace_check`。该分析揭示反例依赖哪些不确定来源，不等于自动判定反例为设计错误。

```tcl
fvtrace_config -check initialstate -severity low -enable
fvtrace_config -check aepnode -severity high -enable
fvtrace_check p_data_correct
```

来源：User Guide，X-2025.06-SP1，第 168–169 页。

### 12.2 `fvtrace_check`：检查已有轨迹中的初始化与未定义行为

```text
fvtrace_check <property_name> [-check <checks>] [-type <types>]
              [-vacuity] [-witness] [-clear] [-quiet]
```

**参数解释。** 属性必须已经有可用轨迹。`-check`、`-type` 限制检查范围，省略时使用已启用的类别；`-vacuity`、`-witness` 选择对应辅助轨迹；`-clear` 清除该轨迹的分析结果；`-quiet` 抑制执行时输出。

**用法与结果。** 未初始化寄存器、被切断的驱动器、黑盒输出、数组越界和显式 X 都可能贡献自由选择。检查应围绕真正影响失败的来源进行，而不是看到任何 X 就把反例忽略。

```tcl
fvtrace_check p_data_correct -check {initialstate undriven aepnode}
fvtrace_report p_data_correct -list
```

来源：User Guide，X-2025.06-SP1，第 169–170 页。

### 12.3 `fvtrace_report`：报告轨迹来源分析

```text
fvtrace_report [<property_name>] [-vacuity] [-witness]
  [-check <checks>] [-type <types>] [-list] [-limit <n>]
  [-xml] [-config] [-no_summary]
```

**参数解释。** 属性和 `-vacuity`/`-witness` 确定轨迹；`-check`、`-type` 筛选类别。`-list` 展开检查项，`-limit` 限制对象数量，`-xml` 输出 XML；`-config` 显示配置而不是结果；`-no_summary` 隐藏汇总。

**用法与结果。** UG 的语法行还出现 `-noSummary` 和缺少横线的 xml，参数解释则明确使用 `-no_summary`、`-xml`；本教程采用参数解释的形式，不重复排版错误。报告之前应已运行 `fvtrace_check`。

```tcl
fvtrace_report p_data_correct -list -limit 50
fvtrace_report -config
```

来源：User Guide，X-2025.06-SP1，第 170 页。

### 12.4 `view_trace`：打开属性或内部等价点的波形

```text
view_trace <property_name> [-rcfile <signal_group_file>]
view_trace -inteq <internal_equivalence_id>
view_trace -deadendID <deadend_id>
```

**参数解释。** 普通属性形式查看对应反例或轨迹；`-rcfile` 复用信号分组设置。`-inteq` 选择 SEQ 内部等价点编号；`-deadendID` 选择约束分析报告中的死路编号。这里汇总 UG 在不同章节展示的调用形式，而非臆造统一的完整平台语法。

**用法与结果。** 死路由约束导致没有合法后继，与 RTL 死锁、活锁不是同一概念。查看死路波形时工具还会显示最后合法状态之后的一段非法变化，用于解释是哪条限制阻断后继；不要把这一段直接作为合法设计反例。

```tcl
view_trace p_data_correct
view_trace p_data_correct -rcfile data_check.rc
# 已获得内部等价编号时可另行使用 view_trace -inteq 3。
```

来源：User Guide，X-2025.06-SP1，第 279，302，565 页。

### 12.5 `compute_reduced_constraints`：寻找某个证明实际需要的较小约束集合

```text
compute_reduced_constraints -property <properties>
  [-subtype <vacuity|witness>] [-block] [-stop]
```

**参数解释。** `-property` 选择已有证明的属性；`-subtype` 可改为分析空洞性或 witness 组件；`-block` 等待完成，`-stop` 停止当前计算。

**用法与结果。** 结果是在保留该证明时可使用的较小集合，不保证全局最少约束。`set_constant` 和 `fvassume -env` 不在此分析支持范围，因此“报告没有需要的约束”也不意味着问题完全无约束。发现某限制导致空洞后，应回到规格审查，而不是直接把剩余限制都删掉。

```tcl
compute_reduced_constraints -property p_data_correct -block
report_reduced_constraints -property p_data_correct
```

来源：User Guide，X-2025.06-SP1，第 303–304 页。

### 12.6 `report_reduced_constraints`：显示证明依赖的约束

```text
report_reduced_constraints [-property <properties>]
                           [-subtype <vacuity|witness>]
```

**参数解释。** 选择属性和可选子类型，报告先前计算得到的约束集合。

**用法与结果。** 该报告说明当前计算中保留了哪些普通约束，不说明每条都唯一必要。应与环境约束、常量和初始化脚本共同审查，避免遗漏隐式限制。

```tcl
report_reduced_constraints -property p_data_correct
report_reduced_constraints -property p_data_correct -subtype vacuity
```

来源：User Guide，X-2025.06-SP1，第 303–304 页。

### 12.7 `get_reduced_constraints`：返回较小约束集合供脚本处理

```text
get_reduced_constraints [-property <properties>]
```

**参数解释。** 给出属性时返回对应集合；省略时返回已有结果的所有属性之约束并集。

**用法与结果。** 集合可用于统计或审查，但不应直接在原任务中批量禁用集合之外的约束并沿用旧结论。做删减实验应复制任务并重跑证明，明确新结论适用的环境。

```tcl
set needed [get_reduced_constraints -property p_data_correct]
query_objects $needed
```

来源：User Guide，X-2025.06-SP1，第 304 页。

### 12.8 `report_fv_complexity`：分析影响属性的设计结构

```text
report_fv_complexity [-stopif <expression>] [-stops <objects>]
  [-list] [-verbose] [-col] [-limit <n>] [-level <n>] [-xml <file>]
  [-filter <expression>] [-regexp] [-nocase] [-bit]
  [-disable_abstraction] [-design] [-instrumented] [-include <types>]
  [-complement] [-property <properties>] [-output_mode <mapped|unmapped>]
  [-subtype <vacuity|property|witness|all>]
  [-usage <assert|assume|cover|all>] [<objects>]
```

**参数解释。** `-property` 或位置对象指定起点；多个起点按影响集合并集统计。`-stops` 指定停止对象，`-stopif` 按属性表达式停止搜索。`-list` 展开对象，`-verbose` 增加位宽和源码位置，`-col` 返回集合；`-limit` 默认报告 100 项，-1 不限制，作用于这些展开形式。`-level` 只用于按层次迭代的报告，不能与显式起点混用。`-xml` 保存结构化报告，`-gui` 是原文另列的图形显示开关。

`-filter` 筛选，`-regexp` 和 `-nocase` 控制模式匹配。默认按字统计，`-bit` 更精确但更慢。`-design` 默认包含设计对象，`-instrumented` 包含工具插装对象，`-include` 可纳入 leaf_module、constraint、latch_loop、combo_loop。`-complement` 查看影响范围之外的对象，`-disable_abstraction` 关闭复杂算子抽象以检查真实结构。`-output_mode` 仅适用于 SEQ；`-subtype` 默认 property，`-usage` 默认 all。

**用法与结果。** 影响范围大说明可能困难，但不是证明所需逻辑的精确集合。结构识别依赖 RTL 和综合形式：门级搭出的加法器不一定被识别为加法算子。调优时应把复杂度与实际求解时间、深度和 formal core 一起看。

```tcl
report_fv_complexity -property p_data_correct -verbose -limit 100
report_fv_complexity -property p_data_correct -bit
report_fv_complexity -level 1 -xml complexity.xml
```

来源：User Guide，X-2025.06-SP1，第 719–734 页。

### 12.9 `get_fv_complexity`：返回影响范围中的结构集合

```text
get_fv_complexity [-stopif <expression>] [-stops <nets>]
  [-list] [-verbose] [-limit <n>] [-level <n>]
  [-filter <expression>] [-regexp] [-nocase] [-bit]
  [-disable_abstraction] [-design] [-instrumented] [-include <types>]
  [-complement] [-output_mode <mapped|unmapped>]
  [-property <list-or-collection-of-properties>]
  [-subtype <vacuity|property|witness|all>]
  [-usage <assert|assume|cover|all>] [<objects>]
```

**参数解释。** 筛选、层次、位级、抽象和对象种类与复杂度报告中的相应概念一致。这里的 `-limit` 默认不限制，而 `report_fv_complexity` 展开报告默认 100 项，不能按同一个默认值解释。`-level` 同样不能与显式起点混用。 `-property` 指定属性列表或集合；`-subtype` 选择属性本体、空通过目标或见证目标，默认 `property`；`-usage` 选择断言、假设、覆盖或全部用途，默认 `all`。末尾对象可以是名称、编号或集合。

**用法与结果。** 返回集合用于自动化分析；需要纯文字报告时使用 report 命令。对象返回数量变化还可能来自位级/字级选择和工具插装对象是否包含，比较两次实验前应固定这些设置。

```tcl
set cone [get_fv_complexity p_data_correct]
query_objects $cone
```

来源：User Guide，X-2025.06-SP1，第 727–731 页。

### 12.10 `compare_coi`：比较两个属性或集合的影响范围

```text
compare_coi [-prop1 <property>] [-set1 <collection>]
  [-props <properties>] [-set2 <collection>] [-prop2 <property>]
  [-list] [-verbose] [-col] [-bit] [-limit <n>] [-filter <expression>]
```

**参数解释。** 第一侧用 `-prop1` 或 `-set1`；第二侧用 `-props` 比较一组属性，或用 `-prop2`、`-set2` 比较单个对象/集合。`-list`、`-verbose`、`-col` 决定显示或返回方式，`-bit` 使用位级分析；`-limit` 默认 1000，-1 不限制，`-filter` 进一步筛选。

**用法与结果。** 用于判断共享逻辑、包含关系和互不相交的结构范围，帮助选择任务分组或解释某约束为什么可能影响多个断言。影响范围相交不等于逻辑上必要依赖，仍需结合实际证明或较小约束集合分析。

```tcl
compare_coi -prop1 p_data_correct -props [get_props -usage assume]
compare_coi -prop1 p_data_correct -prop2 p_count_range -list
```

### 12.11 `is_in_fanin`：查询指定信号是否在目标扇入中

```text
is_in_fanin [-signals <signals>] -lookUpSignals <lookup_signals>
  [-property <properties>] [-seqDepth <depth>] [-col] [-bit]
  [-coi_match <any|all>] [-file <filename>]
```

**参数解释。** `-signals` 或 `-property` 指定搜索起点，`-lookUpSignals` 是必须寻找的信号。`-seqDepth` 限定时序深度，`-bit` 位级查找，`-col` 返回找到的信号集合。`-coi_match any` 默认只需在任一起点扇入出现，all 要求在所有起点都出现；`-file` 保存报告。

**用法与结果。** 适合确认属性是否真正关联目标数据、复位或控制信号。信号不在结构扇入中常提示检查绑定错误或规格漏写，但信号在扇入中也不保证被充分约束或验证。

```tcl
is_in_fanin -property p_data_correct \
```

### 12.12 `set_abstractions`：用较简单模型代替复杂结构

```text
set_abstractions -construct <construct_thresholds>
  [-using <abstraction_model>] [-filter <expression>] [-remove] [-global]
```

**参数解释。** `-construct` 指定结构及尺寸阈值，例如 `{mult=8 div=8 count=8}`；常见结构还包括 add、sub、mod、array、vector、array_comb、vector_comb。默认 snip 用自由变量代替复杂结果。`-using keyvals` 将计数器分成关键值区间；`+linearize` 保留递增/递减方向，仍允许区间内跨步。可增加用户关键值，或使用 user/range 相关组合；具体组合以本章展示的支持形式为限。`-filter` 限定对象，`-remove` 撤销，`-global` 应用于所有任务。

**用法与结果。** 必须在读入设计之后使用，因此主要改善形式模型和求解，不减少 RTL 读入时间。保守抽象扩大行为集合：证明成功通常可支持原问题，但失败可能是抽象引入的伪反例。添加约束精化抽象时，必须保证没有删除原设计的合法行为。

```tcl
set_abstractions -construct {mult=16}
set_abstractions -construct count=4 -using keyvals+linearize
report_abstractions -verbose
# 对照实验需要恢复时：
set_abstractions -construct {mult=16} -remove
```

来源：User Guide，X-2025.06-SP1，第 744–749 页。

### 12.13 `report_abstractions`：核查实际生效的抽象

```text
report_abstractions [-list] [-verbose] [-construct <construct_thresholds>]
```

**参数解释。** 无参数汇总已抽象结构数量；`-list` 给出结构、尺寸、模型和被驱动网络；`-verbose` 进一步列出输入、关键值等；`-construct` 只报告指定类型与阈值。

**用法与结果。** 该报告用于确认抽象是否真正命中目标结构。计数器位宽较小、结构未被识别或过滤名称不对，都可能使设置未起预期作用。返回 1 表示报告命令成功，不是形式证明通过。

```tcl
report_abstractions
report_abstractions -list
report_abstractions -verbose -construct mult=16
```

来源：User Guide，X-2025.06-SP1，第 748–750 页。

### 12.14 `compute_proof_assist`：定位证明代价随深度增长的原因

```text
compute_proof_assist [-block] [-stop] [-property <properties>]
  [-depth <n>] [-minimize <regs>] [-profiler <p0|p1>]
  [-ignore_status] [-live_update <core|depth|all>] [-config <settings>]
```

**参数解释。** `-property` 选择目标；`-depth` 默认 1000，通常需要目标已有至少一层检查结果，未完成或失败属性所选深度应与已有结果相容。`-ignore_status` 允许不按原状态限制启动分析。`-minimize regs` 尝试减少核心寄存器；p0 收集核心、深度和时间，p1 还收集求解工作量且为默认。`-live_update` 选择实时更新内容。`-config` 用 `{profiler=p1,depth=100}` 设置后续默认值，空列表查询当前值。

**用法与结果。** 此功能在该版本明确支持 FPV 和 FRV。它是性能诊断，不是把未完成属性直接转成证明；建议先看哪一深度引入了存储器、长计数或昂贵属性逻辑，再决定改写还是抽象。

```tcl
compute_proof_assist -property p_data_correct \
  -depth 20 -profiler p1 -ignore_status -block
report_proof_assist -last_depth -verbose -advisor
```

来源：User Guide，X-2025.06-SP1，第 752–754 页。

### 12.15 `report_proof_assist`：解释性能分析与建议

```text
report_proof_assist [-xml] [-verbose] [-depth <n>]
  [-constraints] [-comb] [-bit] [-target <registers>] [-last_depth]
  [-top_signals <n>] [-last_cores <n>] [-explicit_cycles]
  [-property <property>] [-coi] [-note_truncation <on|off>]
  [-advisor] [-advisor_level <0|1|2|3>] [-report_cutoff <n>]
  [-engine <engine>] [-model <model>] [-intent <intent>]
  [-mode <mode>] [-config <settings>]
```

**参数解释。** `-depth`、`-last_depth`、`-last_cores` 限定深度或核心序列，`-explicit_cycles` 不合并相似周期。`-constraints` 包含约束，`-comb` 包含组合逻辑，`-bit` 位级显示；`-target` 聚焦寄存器，`-top_signals` 和 `-report_cutoff` 限制显示数量。`-coi` 还显示指定深度内不在核心中的影响对象。`-xml`、`-verbose` 控制输出格式和细节。

`-advisor` 添加建议；`-note_truncation` 默认 on，按原文截到 80 字符。`-advisor_level` 是两位开关，最低位控制复杂度说明，第二位控制下一步 Tcl 建议，默认 2。`-engine` 可用 all、deepest 或 fc1–fc5，默认 deepest；`-model` 可用 all、def、deepest 或模型名。`-intent` 为 bug-hunting、coverage、proof、all，默认 all；`-mode` 为 core-buildup 或 comparative。`-config` 支持相应默认设置，空列表只查询。

**用法与结果。** 最高代价信号只是候选原因。若昂贵部分主要来自属性本身，应先检查不必要的深层 `$past`、复杂匹配或参考模型；若来自真实数据通路，再考虑保持规格正确性的拆分和抽象。不要未经复核直接执行自动建议中的限制。

```tcl
report_proof_assist -last_depth -verbose -comb -constraints
report_proof_assist -advisor -advisor_level 3 -intent proof
report_proof_assist -mode comparative -depth 20 -engine all
```

来源：User Guide，X-2025.06-SP1，第 754–756 页。

### 12.19 `check_constraints`：检查环境约束之间的冲突

```text
check_constraints [-block] [-ccDepth <depth>]
```

**参数解释。** `-block` 等待检查结束；`-ccDepth` 指定该次约束检查的展开深度。此处是 UG 给出的调用形式，不把它扩展成未提供的完整平台命令定义。

**用法与结果。** 约束冲突意味着环境在某个初始状态或某段执行后没有合法的后续行为。即使没有用户断言，也可以执行约束检查。有限深度内没有发现冲突不代表所有无限执行都存在；约束造成的无后续路径也不能直接当作 RTL 状态机死锁。

```tcl
check_constraints -block -ccDepth 4
report_constraints -list -verbose
```

### 12.21 `fvtrace`：把已有轨迹导出为 FSDB

```text
fvtrace [-reset] [-property <propName>] [-vacuity <propName>]
        [-witness <propName>] [-inteq <id>] [-file <fileName>]
        [-composite] [<propName>]
```

**参数解释。** `-reset` 导出初始化复位轨迹；`-property` 导出属性轨迹；`-vacuity` 和 `-witness` 分别选择空通过分析轨迹和见证轨迹；`-inteq` 选择 SEQ 内部等价项。`-file` 指定输出文件名，默认使用属性名和时间戳。`-composite` 合并复位轨迹与属性轨迹。

### 12.22 `snip_driver`：切断内部网络的驱动关系

```text
snip_driver <net>
```

**参数解释。** `<net>` 是展开设计中的网络。这里列出 UG 与快速参考中出现的基本调用，不据此推测完整平台选项。切断驱动后，下游不再由原有逻辑唯一确定该网络的值。
