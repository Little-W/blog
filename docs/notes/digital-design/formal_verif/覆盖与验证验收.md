# 覆盖率评估、验证质量与结果验收

## 1. 为什么不能只报告“全部属性通过”

形式验证的前提之一是必须有人编写有意义的属性。若一个仲裁器只检查“不存在两路同时授权”，这条性质即使被完整证明，也无法证明“有请求时必须给予授权”。因此验证验收需同时审查三个层面：属性是否正确、属性是否涵盖规格、证明是否完成。

### 1.1 四种互补的检查手段

| 方法 | 回答的问题 | 局限性 |
| --- | --- | --- |
| 断言证明（FPV） | 已编写规则是否永不违反 | 无法覆盖未编写的规格 |
| 触发/行为覆盖（SVA cover） | 关键事件是否可达 | 一条路径可达不代表全部情况正确 |
| 代码覆盖与可达性（FCA） | 未覆盖代码是否真的不可达 | 模型与约束可能过度限制 |
| 属性敏感性（FTA） | 注入错误能否被断言检测 | 故障集合有限、求解可能未完成 |

断言证明、可达性分析、属性对设计的关联分析以及故障敏感性分析，对应不同的验证盲点。断言全部通过时，仍应确认关键场景实际可达、关键寄存器受到约束，以及设计行为被有意义地改变后断言会失败。任何单一指标都不足以替代规格评审。

结合这些方法可以发现验证薄弱区域，但不能把它们的百分比相加为“验证完成度”。

## 2. 建立规格—属性对应表

| 规格项 | 属性名称 | 覆盖目标 | 输入前提 |
| --- | --- | --- | --- |
| FIFO 上溢保护 | `AP_FIFO_DEPTH` | `CP_FIFO_FULL` | `push` 为请求 |
| 请求应答最多 3 拍 | `AP_REQ_ACK` | `CP_REQ_ACCEPT` | 合法请求被受理 |
| 复位后中断清零 | `AP_RST_IRQ` | `CP_RESET_RELEASE` | 正确复位时序 |

实际工程中，一条规格可以对应多条断言和多个覆盖目标。记录应保留这种一对多关系，并为每条前提注明依据。比如 FIFO 的满保护既需要检查计数不超范围，也需要检查满且没有同时读出时写指针不移动；“FIFO 已经到满”则是独立的可达性目标，不应拿断言证明状态替代。

记录还应包含：类型、证明状态、评审状态。本例中的运行状态和评审状态均为待完成，不能作为实际验证结果。

这是交付模板，不是某次工具运行产生的真实状态。真实报告不应把未运行的规则写成 `Proven`。当规格中某项只能通过仿真、人工审查或系统测试验证时，要明确标注验证方式，而非制造一个看似覆盖它的空洞断言。

## 3. 验收需要保留哪些文件

```text
release/
├── manifest.yaml         # 设计与工具版本、校验和、资源配置
├── requirements.csv      # 规格与属性对应
├── assumptions.md        # 环境约束的来源和证明影响
├── properties.sv         # 提交时实际编译的 SVA
├── run.tcl               # 运行与初始化脚本
├── report_fv.txt         # 原始工具输出
├── summary.csv           # 属性状态汇总
├── waivers.md            # 豁免理由与审批
└── known_limits.md       # 未完成目标与后续验证计划
```

使用工具本身的 `save_session` 可保存调试数据，但不能替代可读的人类审核记录。运行结果需保留对应的源码版本和相关中间配置，避免以后找不到相同的证明环境。

## 4. 对“Proven”的独立复核

每条关键属性应检查：前件是否在某条合法路径上发生；`disable iff` 是否意外关闭主要检查阶段；假设有没有直接限制被验证的 DUT 内部状态；证明对象是否因黑盒化而改变；目标时钟和复位是否正确。建议将首次建立的属性在仿真中加入一两个故意错误版本，确认它确实能够检测到预期缺陷。

## 5. 不完成或豁免的处理要求

| 情况 | 是否允许直接归类“通过” | 必须补充的信息 |
| --- | --- | --- |
| `Falsified` | 否 | 反例分析、RTL/SVA/约束归因 |
| `Inconclusive` | 否 | 当前资源、证明难点、替代验证方案 |
| `Disabled` | 否 | 禁用依据及是否存在未覆盖规格 |
| `Waived` | 不能自动等同于通过 | 责任人、规格依据、审核和到期条件 |
| `Uncoverable` | 不是功能证明 | 约束可达性及覆盖目标定义 |

豁免是带理由保留的例外，不是对证明状态的改名。不可达目标应记录约束条件和证明证据；未完成目标应记录分析深度、资源限制及剩余风险；明确不属于当前产品配置的目标，应记录配置依据。修改 RTL、规格或约束后，原豁免必须重新评估。

## 6. 组合使用 FCA 与 FTA

FCA 可优先帮助识别没有在正常运行配置下被触发的代码或状态；FTA 可进一步研究即便某区域可达，目前的断言是否能够检测改变。比如一个状态机的两个分支都可达，但错误地交换两路输出后当前断言仍不能发现，这显示需要更有针对性的输出行为属性。

## 7. 质量评审问题

1. 验证的 DUT 顶层和参数是否就是准备交付的版本？
2. 所有必检属性数量与规格表是否一致？
3. 属性是否均具有时钟、复位和输入前提说明？
4. 有无过度约束或从未触发的关键断言？
5. 所有失败与未完成是否已分类处理？
6. 自动生成的属性、覆盖目标及豁免是否经过审核？
7. 更改初始化脚本或工具版本后是否重新运行？
8. 有无保留完整的报告、运行命令及可重现文件？

## 8. 自动化结果摘要

如果需要脚本自动解析 `report_fv`，应优先采用该工具版本明确支持的机器可读输出，避免仅靠模糊匹配报告文本中的 `pass` 或 `fail`；结果里可能同时包含不同应用下的覆盖和断言状态。发布检查脚本 `脚本与工具/validate_publication.py` 检查文件结构、引用路径和代码示例，不是 VC Formal 报告解析器。

## 9. 命令语法、参数与用例

| 命令 | 主要作用 |
| --- | --- |
| `compute_formal_core` | 计算某个证明使用的形式核心 |
| `report_formal_core` | 报告证明涉及和未涉及的设计对象 |
| `get_formal_core` | 返回形式核心对象集合 |
| `snip_formal_core_complement` | 创建切断核心外部寄存器的诊断任务 |
| `check_config` | 在证明过程中同步计算形式核心 |

形式核心描述证明实际依赖的结构，覆盖与验收仍须结合规格责任、环境合理性和不可达原因。没有进入证明核心的逻辑不自动等同于无用逻辑；只有明确分析对象与条件，结果才能用于判断属性集是否存在遗漏。

### 9.1 `compute_formal_core`：计算某个证明使用的形式核心

```text
compute_formal_core [-block] [-stop] [-property <properties>]
  [-subtype <vacuity|witness>] [-depth <n>]
  [-goalIds <ids>] [-proof <proof_name>] [-minimize <regs>]
```

**参数解释。** `-property` 选择属性，`-subtype` 选择辅助组件，`-depth` 请求有界核心。`-goalIds` 与 `-proof` 只适用于 SEQ；`-minimize regs` 尝试减少寄存器，代价可能增加，不能理解为找到全局最小核心。`-block` 等待完成，`-stop` 停止。

**用法与结果。** 核心必须与它支持的结果种类一起解释：完整证明核心、有界核心以及计算未完成不是同一种证据。该章节对默认增量行为、无 `-depth` 的状态选择和示例注释有不一致叙述，因此批处理示例显式选择 proven 属性；分析有界结果时显式给出深度并核对报告。

```tcl
compute_formal_core -property [get_props -status proven] -block
report_formal_core -union -verbose
```

来源：User Guide，X-2025.06-SP1，第 862–864 页。

### 9.2 `report_formal_core`：报告证明涉及和未涉及的设计对象

```text
report_formal_core [-subtype <subtypes>] [-property <properties>]
  [-list] [-no_summary] [-verbose] [-complement] [-union]
  [-runStatus <completed|scheduled>] [-status <proven|bounded|no_status>]
  [-exclude_constraints] [-goalIds <ids>] [-proof <proof_name>]
  [-comb] [-bit]
```

**参数解释。** `-union` 求所选属性核心并集，`-complement` 查看其外部对象；`-property` 限定属性。`-list`、`-verbose`、`-no_summary` 控制显示；`-runStatus` 筛选计算进度，`-status` 筛选核心证据状态。`-exclude_constraints` 排除仅由约束贡献的寄存器/输入；SEQ 可用 `-goalIds`、`-proof`。`-comb` 包含组合逻辑，`-bit` 按位统计，两者不应同时使用。

**用法与结果。** 环境约束与 `set_constant` 是隐式背景，不会全部显式列出；加密区域的寄存器也不一定显示。核心之外不代表功能无需验证，核心之内也不代表所有功能已检查。位级与字级统计分母不同，不能直接比较百分比。

```tcl
report_formal_core -union -verbose
report_formal_core -complement -verbose
report_formal_core -comb -union
```

来源：User Guide，X-2025.06-SP1，第 864–868 页。

### 9.3 `get_formal_core`：返回形式核心对象集合

```text
get_formal_core [-property <property>] [-subtype <subtype>]
  [-complement] [-registers] [-inputs] [-constraints]
```

**参数解释。** 必须选择 `-registers`、`-inputs`、`-constraints` 中至少一种。`-property` 限定属性，`-subtype` 可选择 vacuity、witness 或普通组件；`-complement` 返回核心之外的对象。

**用法与结果。** 使用工具集合函数查询结果。该接口不是获取“所有已验证代码行”，不能把寄存器集合直接当成需求覆盖率。

```tcl
set outside [get_formal_core -property p_data_correct -registers -complement]
query_objects $outside
```

来源：User Guide，X-2025.06-SP1，第 869–870 页。

### 9.4 `snip_formal_core_complement`：创建切断核心外部寄存器的诊断任务

```text
snip_formal_core_complement -property <property>
  [-par_task <parent_task>] [-new_task <new_task>]
```

**参数解释。** `-property` 必填，指定已有核心结果的目标；`-par_task` 指定父任务，`-new_task` 命名新任务。

**用法与结果。** 它用于判断核心之外的大量状态是否拖慢证明。切断会增加自由行为，出现失败可能是伪反例；该实验不能直接代替原模型的验收。应保留父任务不变，并审查新任务的抽象及结果传播关系。

```tcl
compute_formal_core -property p_data_correct -block
snip_formal_core_complement -property p_data_correct \
  -par_task FPV -new_task core_only_experiment
```

来源：User Guide，X-2025.06-SP1，第 868–869 页。

### 9.5 `check_config`：在证明过程中同步计算形式核心

```text
check_config [-formal_core <off|proven|inconclusive|both>]
```

**参数解释。** `-formal_core` 选择对已证明、有界未完成、两者或都不计算。必须在 `check_fv` 前设置才会作用于这轮运行。

**用法与结果。** 这是 `check_config` 的形式核心配置用法，不应与 `check_fv_setup` 或 `fv_setup_config` 混淆。它增加或调整分析证据的收集，不改变用户断言的规格含义。

```tcl
check_config -formal_core proven
check_fv -block
report_formal_core
```

来源：User Guide，X-2025.06-SP1，第 870 页。
