# 形式验证工程组织与结果判读

## 1. 从设计需求建立验证对象

建议为每条规则建立一行审查记录：`需求编号`、`自然语言规则`、`采样时钟`、`复位条件`、`触发条件`、`允许的延迟`、`输入假设`、`属性名称`、`覆盖见证`、`报告状态`、`评审人`。自然语言规则应足够具体，使不接触 SVA 的设计工程师也可以判断反例究竟违反了什么。

例如，规则 **REQ-03：接受请求以后最迟在第 3 个时钟上升沿给出应答**，并不意味着 `req` 一高就要出现 `ack`。首先确认接受发生在 `req && ready`，请求是否允许撤回，`ack` 是脉冲还是电平，以及响应期间能否接受第二个请求。只有这些定义明确后才能编写正确的 SVA。

## 2. 推荐项目目录

```text
project/
├── rtl/                    # 待验证设计，不得含隐含形式假设
├── formal/
│   ├── properties.sv       # 断言、假设、覆盖目标
│   ├── bind.sv             # 可选的非侵入式绑定
│   └── waivers/            # 带原因、审核与到期条件的豁免
├── scripts/
│   ├── setup.tcl           # 通用编译、时钟、复位
│   ├── run_fpv.tcl         # 应用专属检查
│   └── filelist.f
├── reports/                # 文字和机器可读报告
├── sessions/               # 会话与可视化调试数据
└── README.md               # 软件版本、运行命令与结论
```

不要把运行日志与 RTL 混在一起，也不要提交可能包含许可证、客户路径或公司机密的整个工具工作目录到公开代码仓库。

## 3. 完整执行顺序

![可复现验证流程](插图/04_执行流程.svg)

### 3.1 编译通过不代表环境正确

第一步执行 `read_file` 或 `analyze/elaborate`，核对顶层、模块实例、语言、参数值。第二步执行时钟与复位定义，保存初始化状态。第三步执行 `report_blackbox`、`check_fv_setup`，确认没有未预期的黑盒和关键错误。第四步查看属性数量与类型；如果有 20 条预期断言但报告只列出 3 条，必须在求解前调查。

### 3.2 先验证假设，再验证 DUT

优先运行简单覆盖目标：复位退出、请求出现、握手成功、缓冲区填满、缓冲区清空和错误条件能够触发。若关键事件覆盖目标不可达，先检查假设是否过度限制输入。输入假设应有规格出处；特别禁止为了获得 `Proven` 把 DUT 输出或内部状态直接约束为正确取值。

### 3.3 先短后长的证明计划

第一次运行用较短时间验证环境完整性与可发现的浅层缺陷；第二次把剩余难属性按功能块分组，按重要性分配时间、内存与计算节点；最终运行固定输入版本并记录工具版本、命令与状态。这样既能早发现工程错误，又能减少在错误环境里长时间求解的成本。

## 4. 读懂反例：逐周期定位

反例至少应该包含：属性触发周期、导致失败的周期、触发前的设计状态、相关输入变化、reset 状态、接受信号与相关时钟。检查时按顺序回答：

1. 是否处于允许的运行状态？复位是否已结束，起始状态是否合理？
2. 是否违反接口对输入的要求？如果是，应该将其写成环境假设还是 DUT 应处理的非法输入？
3. 失败的准确周期是什么？`|->` 与 `|=>` 是否写反？`$past` 是否在未初始化时使用？
4. 内部状态在此周期之前如何变化？是否存在 NBA 更新与 SVA 采样的时间差？
5. 是否人为加入抽象/黑盒而导致不可行状态？
6. 修改 RTL、修正规格描述还是修改属性？必须区分并留下审查记录。

### 4.1 反例说明模板

```text
属性：AP_FIFO_NO_OVERFLOW
模块版本：rtl_commit=...
实际检查范围：posedge clk；disable iff(!rst_n)
失败位置：反例第 17 周期
输入：push=1, pop=0, full=1
状态：occupancy=8（DEPTH=8）
期望：不得接受写入，occupancy 保持 8
实际：occupancy 变为 9
处置：修复计数更新条件，并添加满状态覆盖目标
```

以上代码块只是一条**假设性的教学反例**，并非本手册实际运行 VC Formal 得到的结果。

## 5. 证明状态与报告编写

必须报告属性总数与分布，包括 `Proven`、`Falsified`、`Inconclusive`、`Covered`、`Uncoverable`、`Disabled`、`Waived` 及其他输出状态。对每条断言写清时钟、复位、有效前提和设计版本。`report_fv -list` 适合总览；`report_fv -verbose` 适合排查；对单条失败使用 `view_trace -property <name>`。`report_fv` 字段随应用和版本有区别，不能把若干种状态强行压成“通过/失败”二选一。

### 5.1 “Proven” 与“覆盖完整”分别检查

强断言 `assert property(req |-> ack)` 被证明，但 `req` 从未出现，其结论仍可能是空洞的。一般需要独立的触发覆盖目标。验证完成至少检查：断言是否被启用、关键 antecedent 可达、是否存在矛盾假设、证明是否包含完整设计范围、所有豁免是否有审查依据。

### 5.2 为什么未完成不等于失败

`Inconclusive` 仅说明当前求解资源与方法不足；可能是大整数运算、内部存储阵列、长时间依赖、跨多个控制状态或过大影响锥导致。应尝试简化断言、拆分属性、建立合法的不变量和合理抽象，而不应直接增加一个使属性易证但不合理的假设。

## 6. 时钟、复位与环境建模审查

| 对象 | 必须核对的问题 | 常见错误 |
| --- | --- | --- |
| 主时钟 | 哪一边沿更新/采样，是否有门控 | SVA 在错误边沿采样 |
| 异步复位 | 生效极性和释放关系 | `disable iff` 之外仍使用非法 `$past` |
| 多时钟 | 相位与允许变化时刻 | 错将异步时钟固定同步 |
| 总线数据 | `valid && ready` 时何时稳定 | 把每拍数据都假设不变 |
| 存储器 | 上电初值与读写冲突规则 | 将未初始化读数据强制为零 |
| 黑盒 | 哪些信号成为任意值 | 意外屏蔽实现错误 |
| 测试端口 | 正常模式/测试模式的关系 | 为了便于证明错误强制测试端口 |

形式工具不会自动知道板级时钟、电源启动顺序或软件配置过程。工程师应把这些外部条件转成可以审查的模型，并把“真实环境保证的行为”与“希望设计满足的行为”分别写成假设和断言。对未初始化状态作额外固定、把输出当成输入约束，都会缩小可探索的行为范围。

## 7. 小型设计推荐的脚本骨架

```tcl
# 一条教学用途的 FPV 批量运行示例
set_fml_appmode FPV
read_file -top counter -sva -format sverilog -vcs {-f filelist.f}
create_clock clk -period 100
create_reset rst_n -sense low
sim_run -stable
sim_save_reset
check_fv_setup -block
report_fv -list
set_fml_var fml_max_time 1H
check_fv -block
report_fv -list
report_fv -verbose
```

**使用条件**：DUT 的初始状态在该复位配置下正确建立、路径从执行目录解析、属性确实已被编译；本节随后直接给出完整示例；实际使用时仍应补充适合目标设计的复位激励并核验状态。如果缺少许可证，本示例仅是经文档对照的参考脚本，不是已经执行成功的日志。

### 7.1 将骨架落实为完整计数器工程

上一段的 `dut/filelist.f` 是通用名称。下面给出实际顶层、文件列表和全部源码，作为结果判读练习的固定输入。

### 7.1.1 被验证的计数器 RTL

规格：复位后计数为零；使能时从 0 计到 9 后回到 0；没有使能时保持。RTL 文件只包含设计，不把待验证结论写成环境假设。

**保存为 `案例工程/rtl/counter.sv`：**

<!-- source-begin: 案例工程/rtl/counter.sv -->

```systemverilog
module counter (
    input  logic       clk,
    input  logic       rst_n,
    input  logic       enable,
    output logic [3:0] count
);
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n)             count <= 4'd0;
    else if (enable) begin
      if (count == 4'd9)    count <= 4'd0;
      else                  count <= count + 4'd1;
    end
  end
endmodule
```

<!-- source-end -->

### 7.1.2 完整断言与绑定文件

`history_valid` 在复位后建立历史有效标志。`ap_range` 检查范围，`ap_hold` 检查保持，`ap_increment` 检查普通递增，`ap_wrap` 检查回绕；两条 `cover` 检查最高计数值及回绕场景是否能够出现。末尾 `bind` 将检查器接入同名设计信号，不需要修改 RTL。

**保存为 `案例工程/formal/counter_props.sv`：**

<!-- source-begin: 案例工程/formal/counter_props.sv -->

```systemverilog
module counter_props (
    input logic       clk, rst_n, enable,
    input logic [3:0] count
);
  logic history_valid;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) history_valid <= 1'b0;
    else        history_valid <= 1'b1;

  ap_range: assert property (@(posedge clk) disable iff (!rst_n)
      count <= 4'd9);

  ap_hold: assert property (@(posedge clk) disable iff (!rst_n)
      history_valid && $past(!enable) |-> count == $past(count));

  ap_increment: assert property (@(posedge clk) disable iff (!rst_n)
      history_valid && $past(enable && count < 4'd9)
      |-> count == $past(count) + 4'd1);

  ap_wrap: assert property (@(posedge clk) disable iff (!rst_n)
      history_valid && $past(enable && count == 4'd9)
      |-> count == 4'd0);

  cp_reaches_nine: cover property (@(posedge clk) disable iff (!rst_n)
      count == 4'd9);
  cp_wrap: cover property (@(posedge clk) disable iff (!rst_n)
      count == 4'd9 ##1 count == 4'd0);
endmodule

bind counter counter_props u_counter_props (.*);
```

<!-- source-end -->

### 7.1.4 完整运行脚本

依次选择应用、读入设计与 SVA、定义时钟复位、保存初始状态、检查设置、列出属性并开始证明。初始化步骤需要在实际安装环境核对复位状态，不能把声明复位等同于已经完成复位。

**保存为 `案例工程/scripts/fpv_counter.tcl`：**

<!-- source-begin: 案例工程/scripts/fpv_counter.tcl -->

```tcl
# Run from the example project root with: vcf -f scripts/fpv_counter.tcl -batch

read_file -top counter -sva -format sverilog -vcs {-f filelist_counter.f}

create_reset rst_n -sense low
sim_run -stable
sim_save_reset
check_fv_setup -block
report_fv_setup -list
report_fv -list
set_fml_var fml_max_time 1H
set_fml_var fml_max_memory 8GB
check_fv -block
report_fv -verbose
```

<!-- source-end -->

**运行命令（Bash）：**

```bash
# 从包含“案例工程”目录的上一级目录开始。
cd 案例工程
mkdir -p logs
set -o pipefail
vcf -f scripts/fpv_counter.tcl -batch 2>&1 | tee logs/fpv_counter.log
```

**结果阅读。** 在初始状态正确的前提下，正确版预期满足这些断言，并存在到达 9 和回绕的覆盖轨迹。这不是本次 VC Formal 的实际运行结果。这些断言分别覆盖范围、保持、普通递增和回绕；复位值及运行中重新复位仍需结合初始化模型和专用复位检查，不能仅凭范围属性成立就认定全部功能正确。

## 8. 状态回归和证明性能

相同的属性在不同的 RTL、SVA、时钟约束或工具版本下不应直接比较结果。推荐记录固定的 run manifest：源码校验值、文件列表、Tcl 参数、许可证环境、CPU 与内存资源、运行时间、属性状态汇总、工具报告路径。对于复杂设计，建立按功能分类的任务：复位初始化、寄存器读写、主状态机、协议握手、数据通路和异常控制。

## 9. 验收条件建议

一个适合作为版本交付的形式验证结果包通常应满足：所有必检断言均明确列出；失败已定位和评审；未完成属性标出后续验证措施；所有豁免有理由与责任人；约束集合经过独立审查；关键触发条件有覆盖见证；代码/时钟/复位/工具版本可以重现。这里的“验收”指项目质量要求，而不是 VC Formal 某个按钮自动代表的最终结论。

详见 [调试与证明性能.md](调试与证明性能.md) 及 [覆盖与验证验收.md](覆盖与验证验收.md)。
